## 5. 已知的坑（务必先读）

1. **`node:sqlite` 在 Node 24 仍是实验性 API**（有警告）。E3.1 实测功能可用（WAL/事务/2 万行 OK），但 E3 迁移落地时要写一个启动自检；若不接受实验性，切 better-sqlite3（性能相当，接口层已隔离）。
2. **行为保持型重构必须每步跑 `npm run check`**（双端 typecheck + 181 测试 + 构建）。曾有两次"改完忘了跑/被 shell 短路"导致带病提交，靠测试兜住才没烂尾。
3. **群纪律不要动**：未点名=沉默（不调 SendToUser）、被点名必须开口+收尾文本兜底；`say`/`stay_silent` 旧工具已删，别按旧文档加回来。
4. **停止令的归口**：认词、排队、砍树全在 `runtime/stop-coordinator.ts`；模型不给发停止令的权力。E4 要把"用户亲自发的停止"改成立即生效（当前是等用户回合结束），这是行为变更，单独提交。
5. **投递与幂等仍是 JSON 落盘**（`agent/inbox.ts` 的 `inbox/*.json`、`storage/received-store.ts`；RunLedger 也还是内存实现）；接口已在 `storage/ports.ts` 隔离，SQLite 迁移时并入消息同事务，别在 JSON 上继续叠功能。
6. **投递语义是「至少一次」**：确认前强退，租约到期会按一次失败尝试回收重做（检查点记在 `item.checkpoint`）。恢复时怎么用检查点（不盲目重跑、unknown 副作用先核对）是 E3.5/E3.6 的事，别在 InboxProcessor 里补丁式加逻辑。
7. tests 全部用 tmpdir，**不读写用户 `.agentbot`**；`.env`/`.commandcode` 是用户数据，clean 脚本白名单已挡，别动。
8. 桌面端进程可能还挂在后台（本 session 最后一次 `npm run desktop` 启动）；窗口关掉即退。
9. **前端界面变化只有一条来源**：发送只收回执（202），其余全靠 `GET /api/events` 订阅（`web/src/features/events/use-event-stream.ts` → `useChatStream.handleEntry` 按 agentId/roomId 路由）。别往发送响应里塞事件；事件缺字段就改 `EventJournal` 的 payload。前端没有自动化测试：改完用「假模型服务器 + headless Chrome CDP」点一遍（临时 `createAgentServer({ createProvider, allowMissingKey, staticDir })`，输入框选中 `.capsule-input`、发送按钮 `.capsule-action-btn.send`）。
