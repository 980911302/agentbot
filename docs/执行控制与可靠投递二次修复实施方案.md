# AgentBot 执行控制与可靠投递二次修复实施方案

版本：1.0

日期：2026-09-13

审计基线：`a630c68 feat(control): 执行控制与可靠投递主干`

状态：发布阻断，等待按本文完成真实主链路接线

## 0. 文档目的

本文件不是重新描述理想架构，而是针对基线提交的实际代码，给出可直接实施和验收的补齐方案。

当前代码已经存在 `RuntimeControlStore`、`ActivationCoordinator`、`DeliveryService`、`EffectRunner`、`OutboxProjector` 和 `ReplyFinalizer` 等模块，单元测试、类型检查和构建也都通过。但这些模块没有完整控制真实运行路径，因此“类已经写了”不等于“系统已经具备该能力”。

本次修复必须解决以下问题：

1. 每一次模型执行都持有并持续使用有效的 `ActivationTicket`。
2. 每一次有副作用的工具执行都经过持久化的 `EffectPermit`。
3. 停止提交后，旧执行不能再启动模型、调用工具或提交投递。
4. 停止结果必须反映真实在途操作，不能永久停在 `stopping`，也不能提前说“停完了”。
5. 私信和群消息统一经过可靠投递事务；群消息不能绕过 outbox。
6. “已经发送”的展示只能来自真实回执；智能体不能只靠正文冒充已发送。
7. `inputId`、`chainId`、租约和预算必须跨智能体、重试、恢复和重启保持稳定。
8. 收件箱根据结构化回合结果决定 ack、held、retry 或 failed，不能“没抛异常就算完成”。
9. 工作台写操作具有授权范围、动作幂等和资源版本控制。
10. UI 展示的是控制事实，不再从助手正文猜测停止或投递状态。

用量统计不在本次范围内。

## 2. 修复后的唯一主链路

```text
用户/同事/群输入
  → CommandAcceptance / Inbox claim
  → ActivationCoordinator.tryActivate
  → RunSession(ticket + stable ids + lease)
  → RunExecutor.markRunning
  → AgentLoop
      → 只读工具：ticket 当前性检查
      → 写工具：EffectCoordinator.reserve → EffectRunner.start → settle
      → SendToAgent：DeliveryService.commit → OutboxProjector
  → ReplyFinalizer（事实核验，无写工具）
  → 结构化 TurnOutcome
  → ticket 终态 + inbox 终态 + UI 事件

停止命令
  → StopService.commit（线性化点）
  → 撤销 ticket/effect/grant + 暂停旧链
  → 事务外 abort 真实句柄
  → 核对 pending effects
  → settled 或 needs_attention
```

禁止保留以下旁路：

- `RunExecutor` 在没有 ticket 时直接启动模型。
- `InboxProcessor` 自己决定“可以跑”后丢弃 ticket。
- `AgentLoop` 直接执行写工具而不经过 EffectRunner。
- room 发送直接写群时间线并同步导演成员执行。
- HTTP、兼容 API、自然语言停止分别实现不同的停止逻辑。
- 从智能体正文反推“已发送”“已停止”或消息来源。

## 3. 统一运行身份

新增运行时内部对象 `RunAuthorization`。它只能由运行时构建，模型和工具参数不能覆盖其中字段。

```ts
interface RunAuthorization {
  commandId?: string;
  inputId: string;
  chainId: string;
  rootCreatedSeq: number;
  grantId?: string;
  ticket: ActivationTicket;
  lease?: {
    deliveryId: string;
    ownerId: string;
    epoch: number;
  };
  provenance: 'user' | 'agent' | 'room' | 'resume' | 'recovery';
}
```

身份规则：

- `inputId` 是稳定输入身份。用户输入使用被受理的 `clientMessageId/commandId`；同事和群来信使用原始 `deliveryId`。
- `chainId` 是交流因果链，不是任务树。所有下游投递继承原 chainId。
- `treeId` 只表示真实执行所有权，用于 Task 工人停止；普通 `SendToAgent` 不进入任务树。
- `runId` 每次执行尝试都可以变化，不能用它重置动作、预算或输入身份。
- inbox ticket 必须绑定真实 lease；lease 换手后旧 ticket 失效。
- 所有后续工具上下文都从 `RunAuthorization` 读取身份，不再使用 `turnState.treeId` 充当 correlation/chain。

`ToolContext` 至少增加：

```ts
interface ToolContext {
  // 既有字段省略
  authorization: RunAuthorization;
  effectRunner: EffectRunner;
  acceptedDeliveryRefs: string[];
  workbenchScope?: WorkbenchActionScope;
}
```

没有 `authorization` 的生产工具调用必须失败。只有纯单元测试可使用显式 fake authorization，不能提供静默兼容兜底。

## 4. 用户输入主链路修复

### 4.1 受理顺序

`AgentRuntime.acceptMessage` 必须改为：

1. 由客户端稳定 `clientMessageId` 生成或查找 `commandId`；一次请求只生成一个 ID，不能分别随机生成 commandId 和 inputId。
2. 调用 `acceptUserInput` 并保存返回值，不得 `.catch(() => undefined)`。
3. 若控制存储故障，输入可以保存为 received，但不得启动模型；向 UI 返回明确的 `CONTROL_FAULTED`。
4. 创建 `runId`，用 accepted 中的 `chainId/grantId/inputId` 调用 `tryActivate(source='user')`。
5. 只有 `admitted` 才进入 `RunExecutor`；传入完整 `RunAuthorization`。
6. 模型调用前执行 `markRunning(ticket)` 并再次校验 ticket。
7. 回合终态写入后将 ticket 标记为 `settled`。

建议把入口收敛成一个方法：

```ts
type StartRunResult =
  | { kind: 'started'; runId: string; authorization: RunAuthorization }
  | { kind: 'held'; reason: HoldReason }
  | { kind: 'rejected'; code: string };

startAcceptedUserRun(input: AcceptedUserInput): Promise<StartRunResult>;
```

### 4.2 新用户命令与 paused 的关系

- `paused` 阻止的是旧自动协作，不阻止主人明确发来的新命令。
- 新用户命令获得本主体、新 chain 的 grant，但不会全局解除 paused。
- 新任务可以执行；此前 held 的旧信仍保持 held。
- 用户若要恢复旧信、旧任务或整条链，必须使用明确的 resume selection。

### 4.3 失败处理

- 受理失败：不创建模型运行，不显示空助手气泡。
- ticket 在模型启动前失效：运行终态为 cancelled/held，不调用 provider。
- ticket 在模型返回后失效：迟到正文、工具结果和记忆都不能发布为普通消息；只保留审计结果。

## 5. 收件箱与群回合接线

### 5.1 claim 与 ticket 必须绑定

当前 `admit(item): 'run' | 'hold' | 'busy'` 必须改成返回完整决策：

```ts
admit(item: InboxItem, lease: InboxLease): Promise<ActivationDecision>;
```

执行顺序：

1. claim 一封消息并取得 `deliveryId/ownerId/leaseEpoch`。
2. 在同一主体仲裁区内调用 `tryActivate`，传入 lease、原始 inputId、chainId、rootCreatedSeq 和 grantId。
3. `admitted` 时保留 ticket；`held` 时释放租约并写 disposition；`busy` 只释放，不烧 attempts。
4. 进入模型前同时复检 lease 与 ticket。
5. 终态先写控制事实，再投影 inbox 状态。

不要把多封信合成一个 ticket。首版保持一封信一个回合。

### 5.2 根据 TurnOutcome 处理 inbox

统一内部结果：

```ts
type TurnOutcome =
  | { kind: 'completed'; visible: boolean }
  | { kind: 'silent' }
  | { kind: 'blocked'; reason: string; retryable: false }
  | { kind: 'cancelled'; reason: string }
  | { kind: 'incomplete'; reason: string }
  | { kind: 'failed_retryable'; reason: string }
  | { kind: 'failed_terminal'; reason: string };
```

映射规则：

| TurnOutcome | inbox 处理 |
| --- | --- |
| completed | handled/ack |
| silent | handled/ack；只允许同事或群回合 |
| blocked | held/manual_review，不 ack 成成功 |
| cancelled | held 或 cancelled，取决于停止范围 |
| incomplete | held/manual_review |
| failed_retryable | 只有确认无副作用时 nack + 有限退避 |
| failed_terminal | failed，不自动复活 |

`max_iterations`、`tool_limit`、`parked` 和 `cancelled` 不能继续走当前的无条件 `session.ack(ids)`。

### 5.3 自动回合计数

非用户来源的 ticket 在准入事务中原子执行：

```text
读取 chain.automaticRuns
→ 检查 maxAutomaticRunsPerChain
→ +1
→ 签发 ticket
```

以下操作不得重置计数：

- 新 runId。
- 换一个收件智能体。
- inbox 重试或租约换手。
- 进程重启。
- resume 同一 input/task/chain。

达到预算后将消息置为 held/budget_exhausted，只产生一个控制事件，不再用智能体互发“预算到了”的消息。

## 6. 持久副作用许可

### 6.1 当前 EffectRunner 不足之处

当前 `EffectPermit` 只是返回给调用者的内存对象，未写入控制快照；`EffectRunner` 的 pending 也只是进程内 Map。停止事务因此无法捕获真实副作用，`targetEffectIds` 始终为空。

必须新增持久 `EffectRecord`：

```ts
interface EffectRecord {
  effectId: string;
  ticketId: string;
  agentId: string;
  inputId: string;
  chainId: string;
  kind: string;
  resourceScope?: string;
  admittedSeq: number;
  startedSeq?: number;
  settledSeq?: number;
  state: 'reserved' | 'started' | 'settled' | 'cancelled' | 'unknown';
  resultRef?: string;
  errorCode?: string;
}
```

`RuntimeControlStore` 增加 `effects: Record<string, EffectRecord>`。

### 6.2 工具分类

每个工具声明执行性质：

```ts
interface ToolEffectPolicy {
  mode: 'read' | 'write' | 'external';
  resourceScope(args: unknown, context: ToolContext): string | undefined;
  replay: 'safe' | 'verify-first' | 'never';
}
```

- `read`：执行前仍复检 ticket，但不创建写副作用记录。
- `write/external`：必须 reserve EffectRecord，再由 EffectRunner 启动。
- 内部消息、工作台、文件写、Shell、网页外部写操作均属于 effect。
- Shell 即使命令看起来只读，也按声明和策略处理；不能依赖正文猜测绝对安全。

### 6.3 统一启动时序

```text
AgentLoop 收到 tool_call
→ ToolGateway 校验参数与授权
→ activation.assertCurrent(ticket)
→ reserveEffect(ticket, intent) 持久提交
→ EffectRunner.start(effectId)
    → 再次 assertCurrent
    → 原子标记 started
    → 绑定 AbortController/进程句柄
    → 执行实际工具
    → settled / unknown
```

禁止工具实现自行绕过 ToolGateway。旧插件如果缺少 effect policy，默认按 `external + verify-first` 处理，不按只读放行。

### 6.4 内部投递的特殊处理

消息投递不应先 reserve 再跨事务 commit。`DeliveryService.submit` 在同一个控制事务中完成：

1. 校验 ticket/generation/processEpoch。
2. 校验 chain 预算。
3. 检查或建立 action identity。
4. 建立 EffectRecord。
5. 写 committed outbox 与不可变 receipt。
6. 将 effect 直接结算为 settled；若提交结果不确定则 unknown。

这样 stop 和 delivery commit 通过同一事务序列决定先后，不存在“stop 已提交，旧执行随后又发出去”的窗口。

## 7. 停止状态机修复

### 7.1 统一入口

自然语言停止、`POST /api/agents/:id/stop` 和未来 UI 停止按钮都调用同一个 `StopService.stop(command)`。

`AgentRuntime.requestAgentStop` 不再直接返回 `activation.requestStop`；它必须负责：

1. 提交停止事务。
2. 通知 StopCoordinator 取消目标运行及句柄。
3. 异步推进停止状态。
4. 发布结构化 stop 事件。

### 7.2 线性化点

`commitStop` 事务内：

- `generation += 1`，`autoActivation='paused'`。
- 撤销旧 grant 和目标 ticket。
- 找出这些 ticket 所属的 `reserved/started` effect，填入 `targetEffectIds`。
- reserved effect 直接改为 cancelled。
- started effect 保持可核对，并进入 pendingEffects。
- 写入 `StopOperation(state='stopping')`。

事务提交成功以后：

- 旧 ticket 不能启动新的模型或工具。
- 旧 reserved effect 不能进入 started。
- 已提交投递事实继续保留，不能伪装成没发过。

### 7.3 事务外收束

StopCoordinator 根据 `targetTicketIds/targetEffectIds`：

- abort 对应 provider、交互等待、Shell 和真实 Task 工人。
- 普通 `SendToAgent` 收件人不是发送方工人，不向它发送停止令，也不注册为 child。
- 等待 started effect 结束或超时。
- 全部确定结束：更新为 `settled`。
- 有无法确认的外部操作：更新为 `needs_attention`，保留 pendingEffects。

状态转换必须持久化：

```text
stopping → settled
stopping → needs_attention
needs_attention → settled（人工或恢复核对后）
```

不能把普通助手文字“好的，在停”“停完了”当状态。UI 根据 stop event 展示；若保留聊天提示，也必须由平台状态生成。

### 7.4 processEpoch

每次进程启动必须生成新的随机 epoch，绝不能从旧快照恢复为当前 epoch。

推荐实现：

- `RuntimeControlStore.currentProcessEpoch` 是本次 open 时新生成的只读值。
- 加载旧快照后，将旧 admitted/running ticket 视为 stale/revoked。
- 在 scheduler 启动前持久写入新 epoch 和恢复处置。
- 新 ticket 使用 `currentProcessEpoch`。
- `assertCurrent` 比较 ticket 与当前进程值，而不是信任快照里的旧值。

必须用“关闭 store → 重新 open 同一目录”测试 epoch 发生变化，而不是只手工篡改一个 ticket。

## 8. 统一可靠投递

### 8.1 完整投递载荷

outbox 不能只保存字符串。定义：

```ts
interface DeliveryEnvelope {
  text: string;
  images?: InputImage[];
  priority: boolean;
  depth: number;
  source: {
    actorId: string;
    inputId: string;
    chainId: string;
    rootCreatedSeq: number;
  };
}

interface DeliverySubmitInput {
  authorization: RunAuthorization;
  target: { kind: 'agent' | 'room'; id: string; nameAtSend: string };
  envelope: DeliveryEnvelope;
  recipientSnapshot?: Array<{ agentId: string; deliveryId: string }>;
}
```

动作 hash 使用 canonical JSON，包含 actor、input、真实 targetId、text、images、priority 和语义相关参数。不能只 hash 文本，也不能使用可变显示名代替真实 ID。

### 8.2 私信

私信提交事务固定产生：

- actionId、receiptId、deliveryId。
- 完整 envelope。
- 目标快照和 payloadHash。
- 预算扣减。

提交后 OutboxProjector 使用同一个 deliveryId 幂等补写 inbox 与 correspondence。禁止在 `DeliveryService.submit` 之后再手工调用一次 `inbox.enqueue`。

### 8.3 群消息

room 分支也调用 `DeliveryService.submit`，不再直接调用 `workbench.postToRoom`。

提交事务固定产生：

- timelineMessageId。
- 当时的成员快照。
- 每位收件人的稳定 recipientDeliveryId。
- 一个群投递 receipt。

OutboxProjector 分阶段幂等投影：

1. `roomStore.appendIfAbsent(timelineMessageId, payload)`。
2. 对成员逐个 `inbox.putIfAbsent(recipientDeliveryId, ...)`。
3. 保存各成员投影状态。
4. 全部完成后标记 visible；部分失败保持 accepted + pending/failed。

投影只负责落地和唤醒请求，不同步等待成员运行，不返回“N 人开口、M 人沉默”。

### 8.4 投影状态

`DeliveryService.submit` 遇到已有 action 时，必须读取真实 outbox 投影状态，不能永远返回 pending。

建议状态：

```ts
type ProjectionState = 'pending' | 'visible' | 'partial' | 'failed';
```

accepted 只表示平台已经持久受理；只有群时间线投影可查询后才可展示“已发到群里”。

## 9. 防止智能体假装已经发群消息

### 9.1 信任边界

以下内容只能由平台根据 receipt/outbox 生成：

- “已发送给某智能体”。
- “已发到某群”。
- “消息来自某智能体”。
- “发言于某群”。
- 发送时间、目标、正文预览和跳转。

模型正文、Markdown、工具文本和附件标题都不能生成这些平台状态。

### 9.2 工具结果必须返回真实回执

`SendToAgent` 不再只返回字符串，改为结构化工具结果：

```ts
interface DeliveryToolResult {
  content: string;
  metadata: {
    kind: 'delivery';
    receiptId: string;
    actionId: string;
    targetId: string;
    targetKind: 'agent' | 'room';
    projectionState: ProjectionState;
  };
}
```

同时将 receiptId 加入当前 `TurnState.acceptedDeliveryRefs`。模型可以在 `SendToUser.delivery_refs` 中引用，但运行时仍会重新查证。

### 9.3 ReplyFinalizer 的确定性校验

HTTP/tool binding 必须传递真实：

- actorId。
- 当前 `inputId`。
- 当前 `chainId`。
- 当前 turn 已接受的 action/receipt 集合。
- source。

删除当前 `inputId: actorId` 的错误绑定。

回执属于本次动作的判断必须同时满足：

```ts
found.actorId === input.actorId
&& found.inputId === input.inputId
&& input.allowedReceiptIds.includes(found.receiptId)
```

历史证据必须通过单独的 `historical_refs` 模式展示，不能假装为本轮发送。

`claimedTargetId` 不适合表示多次发送；改为逐项 claim：

```ts
interface DeliveryClaim {
  receiptId: string;
  targetId: string;
  targetKind: 'agent' | 'room';
}
```

### 9.4 自由正文的有限语义核查

只验证 refs 仍不足以阻止模型在自由正文里说“我已经发了”。需要只读、无工具的 `DeliveryClaimVerifier`：

输入：候选正文、本次 DeliveryIntent、真实 receipts 和允许公开的目标名称。

输出：严格 JSON，只包含正文里的动作完成声明、对应 target 和 receipt 匹配结果。

处理流程：

1. 用户回合最终正文统一进入 finalizing。
2. 如果本轮存在发送意图、投递工具调用或候选正文可能包含外部动作完成声明，执行一次 verifier。
3. 所有“已发送”声明必须对应本轮 accepted receipt，目标一致。
4. 不支持的声明只允许一次纯文本纠正；纠正阶段不能调用任何业务工具。
5. 第二次仍不合格时，运行时删除不受支持的完成声明，替换为确定性说明，并附真实状态条。
6. 绝不为了让声明变真而自动补发消息。

verifier 提示词保持通用和简洁，不写固定人名、固定群名或故障句子。故障语料只进入离线评估集。

### 9.5 合法无回执场景

- 普通聊天没有投递动作：可以正常回复，不显示“未验证”。
- 用户询问历史、引用别人曾发送：不得误当成本轮完成声明。
- 同事或群回合没有需要回应的内容：允许 silent。
- 用户明确要求发送但没有 accepted receipt：结果必须是 incomplete/blocked，不得说已完成。
- accepted 但尚未 visible：显示“已受理，正在同步”，不能说群里已经可见。

## 10. 工作台写操作

### 10.1 授权不是工具是否可见

智能体装有 CreateAgent/CreateChannel 不代表任何来信都能授权它创建资源。

定义：

```ts
interface WorkbenchActionScope {
  scopeId: string;
  issuedByCommandId: string;
  holderAgentId: string;
  allowedActions: Array<'create_agent' | 'update_agent' | 'create_room' | 'update_room'>;
  maxAgents: number;
  maxRooms: number;
  resourceBounds?: string[];
  delegation: 'none' | 'explicit';
}
```

- 主人直接命令可签发该回合 scope。
- 普通 SendToAgent 只传信息，不传工作台授权。
- 若未来允许委派，必须由单独的结构化授权动作创建子 scope，并共享原额度。
- `MAX_AGENTS_PER_TURN` 可保留为额外防护，但不能作为唯一授权和配额机制。

### 10.2 幂等动作

每个工作台写工具先建立持久 action：

```text
inputId + holderAgentId + toolName + canonical semantic args
→ stable actionId
→ 预分配 resourceId
→ 调用 registry mutation
→ 写 applied revision/result
```

崩溃恢复时查询 action/resourceId：

- 已创建：返回原结果。
- 未开始且 ticket 已失效：取消，不创建。
- 结果未知：核对 registry，不盲目再建。

`UpdateChannel` 必须携带 `expectedRevision`，服务端在一个 mutation 中完成成员增减。不能先 list、在客户端算新集合、再无版本覆盖。

## 11. UI 与 API

### 11.1 控制快照

扩展 agent control view：

```ts
interface AgentControlView {
  agentId: string;
  autoActivation: 'enabled' | 'paused';
  generation: number;
  heldInboxCount: number;
  activeRunIds: string[];
  activeEffectCount: number;
  lastStop?: {
    stopId: string;
    state: 'stopping' | 'settled' | 'needs_attention';
    pendingEffects: Array<{ id: string; reason: string }>;
  };
  faulted: boolean;
}
```

`heldInboxCount` 从 inbox disposition 统计，不能用 revoked ticket 数量代替。

### 11.2 事件

新增或补齐平台事件：

- `control_changed`
- `stop_started`
- `stop_settled`
- `stop_needs_attention`
- `delivery_accepted`
- `delivery_visible`
- `delivery_projection_failed`
- `inbox_held`

事件必须包含稳定实体 ID 和单调版本。前端重复收到或乱序收到时不得复活旧状态。

### 11.3 API 语义

- `POST /api/agents/:id/stop`：202 返回 stopId 和 committed 状态，不伪造 settled。
- `GET /api/control/stops/:stopId`：返回持久 StopOperation。
- `POST /api/agents/:id/resume`：必须选择 input/task/chain/enable_future。
- `GET /api/deliveries/:receiptId`：按可见权限返回事实。
- 未实现 `room_round/all_agents` 时明确返回 `UNSUPPORTED_STOP_SCOPE`，UI 不展示假按钮。

## 13. 实施顺序

### 阶段一：先堵住停止后的新副作用

1. 修复 processEpoch。
2. 用户、inbox、room、resume、recovery 全入口传递 ticket。
3. RunExecutor/AgentLoop 接入 ticket 复检。
4. EffectRecord + EffectRunner 接入所有写工具。
5. StopOperation 推进到 settled/needs_attention。

本阶段完成门：stop 提交后，旧执行的 provider 调用计数和写工具启动计数都不再增加。

### 阶段二：统一投递并修复防假发送

1. DeliveryEnvelope 保存图片和稳定身份。
2. DM 删除提交后的手工 enqueue。
3. room 改走 DeliveryService + OutboxProjector。
4. SendToAgent 返回 receipt metadata。
5. ReplyFinalizer 使用真实 inputId、allowed receipts 和有限 verifier。

本阶段完成门：没有 accepted receipt 时，任何“已发群”声明都不能作为普通成功答复展示；同时普通聊天不产生验证噪音。

### 阶段三：链预算和 inbox 终态

1. chainId 跨发送和收件回合保持不变。
2. 准入事务扣 automaticRuns。
3. InboxProcessor 按 TurnOutcome 处理。
4. 重启和 resume 不重置预算、不重复副作用。

本阶段完成门：构造两个智能体低深度横向互发，达到预算后稳定 held，不再调用模型，也不产生提醒消息风暴。

### 阶段四：工作台、UI 和迁移

1. WorkbenchActionScope 与持久 mutation action。
2. registry revision/幂等创建。
3. 控制快照和事件。
4. 旧 control snapshot 迁移与只读核对。
5. 真桌面端端到端验证。

## 15. 数据迁移

控制 schema 升级时：

1. 启动 scheduler 前完成迁移。
2. 旧 admitted/running ticket 全部标记 stale/revoked。
3. 旧 `stopping` 没有 effect 证据时标记 needs_attention，不自动伪造 settled。
4. 旧 outbox 缺图片、成员快照或稳定 ID 时标记 legacy/unverified，不盲目重投。
5. 旧 action 若无法证明是否已经执行，进入 manual_review。
6. 旧 held/pending inbox 保留原文，不自动恢复整个队列。
7. 迁移前备份数据目录；迁移过程可重复执行且结果相同。

新版本启动顺序固定为：

```text
取得单实例锁
→ 加载并迁移控制存储
→ 生成并提交新 processEpoch
→ 核对旧 ticket/effect/outbox
→ 恢复幂等投影
→ 恢复租约处置
→ 最后启动 scheduler 和 HTTP 自动入口
```

## 16. 提示词边界

提示词只表达行为原则：

- 发消息使用发送工具，工具返回后不等待收件人完成。
- 最终说明必须以工具和平台事实为准。
- 没有需要回应的信息时允许结束。
- 当前群发言和私信出口遵守工具契约。

提示词不得负责：

- 保存 generation、ticket、lease、chain budget。
- 识别幂等动作。
- 判断停止是否真实完成。
- 生成平台“已发送”状态。
- 用固定人物、群名和句式修补故障。

这些必须由代码状态机和测试保证。

## 18. 完成定义

以下条件必须同时成立，才能把“已实现主干”改为“已完成”：

1. 生产环境不存在无 ticket 的模型运行。
2. 生产环境不存在无 EffectPermit 的写工具执行。
3. stop 先提交时，旧执行无法再生成任何新副作用。
4. stop 状态能够确定进入 settled 或 needs_attention。
5. processEpoch 每次重启都变化，旧 ticket 不能复用。
6. DM 和 room 都由同一个 DeliveryService 提交并由 outbox 投影。
7. 图片、目标快照和成员 deliveryId 能跨崩溃恢复。
8. 没有真实回执时，智能体不能向用户展示未经纠正的“已经发群”声明。
9. 本轮回执不能被历史或其他主体的回执冒充。
10. chainId 和预算跨智能体、重试、恢复与重启保持连续。
11. cancelled/incomplete/parked 不会被 inbox 当成成功消费。
12. 普通同事消息不能获得工作台管理授权。
13. 控制状态、投递事实和消息身份由平台元数据展示，不依赖助手正文。
14. R01–R27、完整测试、双端类型检查和构建全部通过。

只增加类、提示词、正则、单元测试或 UI 文案，均不满足完成定义。
