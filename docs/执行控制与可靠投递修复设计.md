## 0. 实施者先读

本次修复的目标是：一个请求能够有边界地结束；用户停止后，相关执行不能被旧来信重新启动；平台能够准确说明消息是否真正发出。

优先处理执行协议，再处理界面。不能只隐藏空白气泡，也不能只增加正则、提示词或 LLM 轮数。

实施环境保持本机单实例、Node/TypeScript、现有 JSON/JSONL 存储和 React/SSE。采用模块化单体，不引入微服务、消息中间件或多实例协调。首版补齐进程崩溃恢复，不宣称断电后绝对持久，也不宣称任意 Shell/外部服务恰好执行一次。

### 0.1 保留的产品约定

- `SendToAgent` 是给同事或群发消息，投递后返回，不等待对方工作完成。
- 同事有独立回合。普通投递不挂到发送方的子任务树；停发送方不自动停独立同事。
- `Task` 工人属于创建者的执行范围，按真实所有权取消。
- 当前群里发言走 `SendToUser`；`to:"dm"` 才私发主人。不能向当前群再调用 `SendToAgent` 唤醒全体。
- 一个智能体有统一对话线；群时间线、同事往来、工具执行分别投影，不能冒充主人消息。
- 一封来信对应一个回合；允许同事和群回合沉默。人直接提出的问题需要得到回答或明确的未完成说明。
- 提示词保持简洁、通用。本文中的故障语料用于回归测试，不得变成提示词里的特例清单。

本次明确修订以下旧行为：

1. 用户的停止命令不再排队等待正在执行的用户任务完整结束。

| 时间（北京时间） | 事实 |
| --- | --- |
| 13:36:27.554 | 张三发送“（不用回）李四 id 发我即可。”，消息积压在收件箱 |
| 13:38:08.506 | 主人发送“停止” |
| 13:38:08.523 | 通用助手消息写入“停完了。” |

| 13:38:13.784 | 对话中出现“已把李四的 id 发给张三。” |

这一轮测试期间，聊天控制面记录为 80 个运行：2 个用户来源运行（原始请求和停止），78 个同事来信运行。停止后通用助手又启动了 12 个同事来信回合。执行账本不包含独立停止命令，因此对应统计为 79，不要把两套统计混用。

这不是同一封信无限重试的证据。现有副作用检查已经阻止了一部分不安全重试；主要问题是同一回合不断制造新的信，新信各自启动新回合。

另需纠正两个推断：

- “发牌员”触发错误只是初始例子。“李四的 id 请发我。收到即拉群开局。”这样的同事私信也被误判，修复不能只排除“发牌员”。
- 新智能体拥有工作台工具本身不必然是权限漏洞。真正要约束的是谁授权了这项操作、计入哪项额度，以及收到普通消息是否代表获得新的工作台管理授权。

## 2. 必须成立的系统不变量

以下是发布阻断条件，不以提示词是否“通常有效”为依据。

1. **统一激活入口**：每次模型执行都持有运行时签发的执行许可；定时器、手动 drain、群回合、续跑、恢复都不能绕过。
2. **停止有持久边界**：停止提交成功以后，旧许可不能批准新的执行或副作用；重启不能恢复这些许可。
3. **收信不等于执行**：消息可被接受和归档，即使收件人已暂停；暂停不应删除消息。
4. **执行所有权与消息关联分离**：`Task` 可级联取消，`SendToAgent` 不因此变成子任务。
5. **投递事实不可由正文产生**：“已发群”“发言于某群”等文字不能生成平台投递状态或修改目的地。
6. **投递成功只证明已提交消息**：不证明成员已经运行、已经回复或业务任务完成。
7. **已经发送不能说成没发送**：取消、返回丢失、投影延迟不能抹掉已提交的投递事实。
8. **同一逻辑动作幂等**：同一输入下重复提交同一投递，返回同一回执，不创建第二封信。
9. **阻塞允许收尾**：创建失败、深度到顶、权限不足、目标未知，都能被如实说明，不要求先制造一个外发错误。
10. **自动交流有总预算**：不同消息 ID 和新 `runId` 不能重置同一因果链的额度。
11. **终态不可复活**：已结束 `runId` 不回到 running；恢复用新 run，保留任务及动作身份。
12. **视图不反向控制执行**：SSE 断开、面板关闭、刷新、空泡过滤不能决定工作是否停止。

## 3. 领域划分与身份

### 3.1 不能再混用的对象

| 对象 | 含义 | 是否拥有取消权 |
| --- | --- | --- |
| 用户命令 `commandId` | 一次明确输入或界面控制动作 | 主人的授权入口 |
| 任务 `taskId` | 同一主体的一项工作，可多次执行 | 仅其所有者及明确授权控制者 |
| 执行 `runId` | 一次具体执行尝试 | 可取消本次执行，不自动撤销已发消息 |
| 执行树 `treeId` | 同一所有者及其真正的工人 | 对工人级联，不包含普通收件人 |
| 因果链 `chainId` | 一个输入引起的消息来往、群扇出和后续回合 | 用于溯源、预算；单凭此 ID 不授予取消权 |
| 消息 `deliveryId` | 一封实际提交的同事信或成员投递 | 消息已经提交的事实不可撤回式改写 |
| 逻辑动作 `actionId` | 同一输入中的一次投递或工作台写操作 | 幂等、回执和重试身份 |
| 回执 `receiptId` | 平台对一次动作的提交证明 | 不授予新操作权限 |
| 展示频道 `channelId` | 私聊、群聊或往来查看面板 | 只控制展示位置 |

`parentRunId` 可以表达执行关联，但不能仅凭它推导“停止整棵协作网络”。`correlationId` 保留为兼容展示字段，不承担预算、权限和任务所有权的多重职责。

### 3.2 稳定输入身份

- 用户输入：使用已受理的 `commandId/messageId`；网络重试由 `channelId + clientMessageId` 找到同一命令。
- 同事来信：使用原始入站 `deliveryId`，不能使用消费时新生成的 `Message.id`。
- 群成员回合：使用该成员的 `deliveryId`，同时保留公开 `roomMessageId/roundId`。
- 恢复与重试：保留 `inputId`、`chainId`、已创建的 `actionId`；只更换执行尝试 `runId`。

这些 ID 由运行时建立、持久化和传递。模型不能通过工具参数指定新的根链、发送身份、权限或控制代次。

## 4. 目标模块边界

```text
HTTP / CLI / UI 控制命令
  → CommandAcceptance（验证、命令幂等、确定受众）
  → ActivationCoordinator（唯一执行许可 / 停止 / 恢复仲裁）
      → RunExecutor → AgentLoop → 工具
      → StopCoordinator（取消句柄、等待收束、报告范围）

SendToAgent / 群 SendToUser
  → DeliveryService（目标、幂等、预算、持久提交、回执）
  → OutboxProjector（时间线 / correspondence / inbox 幂等投影）
  → InboxScheduler（仅发起调度请求）
  → ActivationCoordinator → InboxProcessor → 新回合

ReplyFinalizer（正文出口 / 回执核验 / 有限纠正 / 合法沉默）
  → 消息与控制事件 → ChatEngine → 分类型展示
```

职责约束：

- `ActivationCoordinator` 不调用 LLM，不读取正文猜测停令范围。
- `StopCoordinator` 不自己遍历邮箱触发模型，也不把同事关系重新注册成 children。
- `InboxScheduler` 只负责定时唤醒请求；不拥有准入权。
- `DeliveryService` 不同步执行收件人；不等待回复。
- `OutboxProjector` 只补齐已提交动作的本地记录，不重新规划目标，不调用 LLM。
- `ReplyFinalizer` 不代替模型补做外发；核验阶段没有写工具。
- `ChatRunCoordinator` 继续管理运行事件及 UI 状态，但不能另行授予执行许可。

## 5. 首版存储方案：单一控制事实源 + 幂等投影

### 5.1 确定采用的方案

新增 `RuntimeControlStore`，首版存储为 `.agentbot/control/state.json`。它使用一个串行事务队列和单文件原子替换，统一保存：

- 控制命令幂等记录、单调递增 `controlSeq`；
- `AgentControl`、执行许可/准入记录、停止记录；
- 因果链及额度占用；
- 逻辑动作索引、已提交 outbox 记录、不可变回执；
- 恢复授权、终态和必要的去重索引。

事务内对草稿快照做纯同步状态变换，然后原子写入，成功后替换内存状态并发布控制事件。并发请求不能从旧内存快照分别覆盖同一个字段。

现有 `inbox/*.json` 继续保存队列及租约，`messages/`、群时间线、correspondence 继续保存历史；它们不是新的执行许可事实源。`RunLedger` 保留执行树、工人和恢复描述，不能只凭 open 树自动开跑。`chat/runs.json` 是运行展示与恢复记录，不可绕过控制事实源。

不再用“新增一个 paused.json，各模块先读一下”作为实现。准入、停止、发送提交、预算扣减必须经过同一个串行仲裁点。

### 5.2 为什么不依赖跨文件事务

当前 `writeJsonAtomic` 只保证单文件替换，不能让控制、群时间线、inbox 三份文件一起提交。本方案把投递事实及其固定 ID、完整 payload、目标快照先放进一个控制事务；其余文件只做可重放投影。

因此可处理“提交后还没写 inbox 就崩溃”，而不需要把任意旧模型回合重新执行一遍。

消息正文可能敏感，控制文件和投影使用受限文件权限。只保存本次动作需要的数据，不复制整段上下文。

### 5.3 保留与容量

- 不能使用当前最近 500 条工具日志作为幂等事实源；被裁剪的日志会使已发送动作再次执行。
- 首版不自动删除仍被任务、未处理信、停止记录或恢复动作引用的控制记录。
- 终态 payload 可归档，但动作身份、提交结果及引用关系必须可查询，不能归档后变成“没发过”。
- 为控制快照设置可配置容量上限，初始建议 64 MiB；在较低软阈值（建议 48 MiB）停止受理新增 payload，保留控制、停止、终态、去重及归档的增长空间。拒绝新增动作不等于拒绝停止和收束写入，不能静默丢弃活动数据或去重记录。
- 逻辑预留不能保证物理磁盘不满。实际写入失败走第 7.6 节的失效保护，不能先在内存写 paused 就确认“已持久停止”。必须覆盖快照接近上限时仍可停止的测试。
- 压缩/归档也通过同一事务入口。后续若改 SQLite，实现相同端口和验收契约，不改变业务语义。
- 首版保证正常文件系统上的进程崩溃恢复。若要求断电级持久，需要单独实现文件及目录同步策略并做故障测试，不能在文档中默认已有。

## 6. 执行许可与暂停状态

以下 TypeScript 是领域接口示意，字段名可微调，语义不可省略。

```ts
interface AgentControl {
  agentId: string;
  generation: number; // 该智能体的停止边界；持久递增
  autoActivation: 'enabled' | 'paused';
  revision: number;   // 状态更新版本，不等于 generation
  lastStopId?: string;
  lastStopSeq?: number;
  blockedAutoRootsThroughSeq?: number; // 此序号及以前建立的链默认禁止再自动准入
}

interface ActivationGrant {
  grantId: string;
  agentId: string;
  generation: number;
  issuedByCommandId: string; // 可信用户命令或平台明确控制动作
  issuedSeq: number;
  scope:
    | { kind: 'input'; inputId: string }
    | { kind: 'task'; taskId: string }
    | { kind: 'chain'; chainId: string };
  state: 'active' | 'revoked' | 'closed';
}

interface ActivationTicket {
  ticketId: string;
  agentId: string;
  runId: string;
  taskId: string;
  inputId: string;
  chainId: string;
  generation: number;
  executionEpoch: number; // 现有执行位 fencing，用于抢占/换手
  processEpoch: string;   // 旧进程票据不能跨进程复用
  grantId?: string;
  lease?: { deliveryId: string; ownerId: string; epoch: number };
  admittedSeq: number;
  source: 'user' | 'inbox' | 'room' | 'resume' | 'recovery';
  state: 'admitted' | 'running' | 'revoked' | 'settled';
}
```

`generation`、执行位 epoch、inbox lease epoch、SSE epoch 分别解决不同问题，不合并：停止、抢占、领取换手、事件重放不能相互冒用。

### 6.1 统一准入

必须统一覆盖：

- 普通私聊、群成员被分配的用户新输入；
- `InboxScheduler` 定时触发、`drainInbox` 手动触发；
- `RunExecutor.finally`、`resumeOwed`、`resumeRecovered`；
- 关服重启、租约过期、失败重试；
- 同事消息的 priority、群中的 `@`、后台工人的后续通知。

推荐接口：

```ts
interface ActivationCoordinator {
  acceptUserInput(input: UserCommand): Promise<AcceptedCommand>;
  tryActivate(input: ActivationRequest): Promise<
    | { kind: 'admitted'; ticket: ActivationTicket }
    | { kind: 'held'; reason: HoldReason }
    | { kind: 'busy' }
    | { kind: 'cancelled'; reason: string }
  >;
  assertCurrent(ticket: ActivationTicket): void;
  admitEffect(ticket: ActivationTicket, effect: EffectIntent): Promise<EffectPermit>;
  requestStop(command: StopCommand): Promise<StopReceipt>;
  resumeSelected(command: ResumeCommand): Promise<ResumeReceipt>;
}
```

准入必须同时检查主体存在、控制代次、授权范围、执行位、任务终态、因果链预算，以及领取租约（若有）。

`tryActivate` 的入参从持久消息和命令记录构造，不直接信任 LLM 生成的 `source`、`grantId`、`chainId`。

### 6.2 暂停后各种输入的处理

| 输入 | 保存/展示 | 是否可以执行 |
| --- | --- | --- |
| 停止之前积压的同事信 | 保留往来和待处理状态 | 不自动执行 |
| 停止后才到达的旧链回信 | 正常归档 | 不自动执行；到达时间晚不能洗成新任务 |
| 用户给该智能体的新私聊 | 正常受理 | 按新命令许可执行 |
| 用户新的群发言 | 依据真实用户事件确定受众 | 给相关成员新命令范围的许可，旧群回合不随之恢复 |
| 其他智能体主动发来无新用户授权的消息 | 正常归档 | 无匹配许可则待处理 |
| 用户明确恢复选定旧任务/来信 | 保留原动作及回执 | 检查副作用和权限后新开执行 |
| 定时器、重启、手动 drain | 不制造用户授权 | 不得解除暂停 |

首版采取以下明确决定：**用户的新命令建立新链，并为其明确受众签发该新链的许可；不会将 `autoActivation` 全局改回 enabled。** 这样新任务引起的回信仍可完成协作，但上一个已停止任务的来信不能复活。

群发言的许可在 `AgentRuntime.acceptRoomMessage` 受理时签发：一条群命令建一条新链，给每个在场受众各签发一个覆盖该链的许可（`ActivationCoordinator.acceptRoomInput`），chainId 随群投递进收件箱，`InboxProcessor` 的准入复检据此放行。工作台代发（`roomSenderId`）不是用户命令，停止词也不签发许可。此前群发言完全不签发许可，被停止过的成员在群里永远 held。

新链许可只适用于运行时继承了该 `chainId` 的后续动作，不能凭正文提到新任务、较新的到达时间或重新生成 `runId` 获得。新链无待处理、在途投递、执行及真实工人后可关闭许可；遇到 paused/blocked 项则保留为明确待处理状态，不无限轮询。

许可必须绑定 `(agentId, scope)`：用户私聊甲只给甲签发许可；甲随后联系已暂停的乙，不会靠继承 chainId 给乙签发许可。乙保存来信，等待主人对乙的新命令或明确恢复。普通发送工具和模型都没有签发/扩大 grant 的权限。

“恢复选定旧链”和“开启以后的自动处理”是不同控制动作。后者不自动释放已 held 的历史消息，也不能放行尚未到达的旧回信。每条根链在控制存储建立可信 `rootCreatedSeq`；stop 将主体 `blockedAutoRootsThroughSeq` 提升至本次提交序号。开启未来自动处理只允许比该边界更新的根链，不删除这个边界。缺少可信根序号的旧链进入 legacy/manual_review。

自动准入的关键谓词为：当前代次、执行位、任务、租约和预算均有效，且满足以下之一：①存在覆盖该主体及本项输入的有效 grant；②主体 enabled、根链序号晚于停止边界且本项未 held/cancelled。**仅 enabled 不够，较晚的消息到达时间也不够。** 显式选定恢复可通过新 grant 覆盖旧链限制，但只覆盖所选范围。

```ts
interface ResumeCommand {
  commandId: string;
  requestedBy: { kind: 'user'; id: string };
  agentId: string;
  selection:
    | { kind: 'input'; inputId: string }
    | { kind: 'task'; taskId: string }
    | { kind: 'chain'; chainId: string }
    | { kind: 'enable_future' };
}
```

input 恢复只签发 input grant；task 恢复仅覆盖该主体的同一任务；都不得升级为全链许可。同链其他旧信或后来派生的新输入仍需各自许可。chain 恢复才允许该主体继续所选链的交流，也不能恢复其他暂停主体。恢复不刷新已消耗预算；若需要增加预算，必须另附明确的产品控制范围。已提交动作保持原身份，恢复不代表重做。

## 7. 停止协议

### 7.1 产品语义

默认私聊停止：停止该智能体在命令受理前已获准的工作及它真正拥有的工人，暂停其旧协作的自动激活。

- 用户当前运行即使来源是 `user`，也立即走取消控制路径。
- 独立同事的执行不受影响。同事仍可发信，已暂停主体只保存来信。
- 群停止的范围由显式控制命令确定。新增 `room_round` 或 `all_agents` 必须来自主人控制入口，不能因消息正文写“停止”就取得全局权限。
- 第一阶段必须做 `agent` 范围。界面若提供“全部停止”，则必须完整实现 `all_agents`；未实现前不要展示一个只有文案的按钮。

### 7.2 停止命令与结果

```ts
interface StopCommand {
  commandId: string; // 客户端重试保持不变
  requestedBy: { kind: 'user'; id: string };
  scope:
    | { kind: 'agent'; agentId: string }
    | { kind: 'room_round'; roomId: string; roundId: string }
    | { kind: 'all_agents' };
}

interface StopOperation {
  stopId: string;
  commandId: string;
  scope: StopCommand['scope'];
  committedSeq: number;
  targetTicketIds: string[];
  targetEffectIds: string[];
  state: 'stopping' | 'settled' | 'needs_attention';
  pendingEffects: Array<{ id: string; reason: string }>;
}
```

自然语言精确停止词可继续由现有入口转换成 `StopCommand(scope=当前智能体)`。不要对包含停止词的引用、问题或普通长句做全文匹配。按钮直接传结构化命令。

### 7.3 执行顺序及线性化点

1. 在控制事务中按 `commandId` 去重，同键不同 scope 拒绝。
2. 对 agent/all_agents 范围，将目标智能体 `autoActivation=paused`，递增 generation，提升旧链截止序号，撤销旧 grant，写入停止记录及目标票据和副作用集合。
3. **第 2 步持久提交成功是停止的生效点。** 之后旧票据不能获得新的发送、创建、执行许可。
4. 退出事务锁，取消票据对应的模型调用、工具、Shell/工人、交互等待和适用的后台记忆/压缩句柄。
5. 将已领取但未完成的旧来信转为 held 或需核对；撤销由停止覆盖的自动续跑候选。
6. 等待目标执行及已准入副作用收束。不能只调用 `abort()` 就视作全部结束。
7. 持久写入 `settled`，再对用户显示停止结果。仍有无法确认结束的副作用则保留 `stopping/needs_attention`。

事务锁内不等待模型、工具 Promise 或取消回调，否则它们的 finally 回填可能死锁。控制序号用于顺序判断，不再使用 `createdAt < stop.createdAt` 处理同毫秒并发。

停止后的新用户命令排在新的控制序号上，不属于旧 stop 的目标集合。停止收尾不能把这些新票据也批量写成 cancelled。

`room_round` 是可选的局部范围，不能直接套用主体全局 generation 递增。若实现，须持久保存 round 撤销标记，只撤销该 round 的许可、真实工人和未执行成员投递，所有 gate/effect 检查均叠加 round fence；不停止该成员无关私聊或独立同事。没有实现这套范围检查前，API 对该 scope 明确返回 `UNSUPPORTED_STOP_SCOPE`，不回成功。

### 7.4 已准入副作用的边界

所有有副作用的入口必须拿到 `EffectPermit`，至少包含 ticket、effectId、准入控制序号、资源范围和状态。生命周期为 `reserved → started → settled`，无法确认结果时进入 `unknown`，未启动即取消为 `cancelled`。停止生效前已启动的 OS/网络操作可能已经发生，停止不承诺回滚。

`admitEffect` 只完成 reserved，并立即注册可取消的执行槽。工具必须通过统一 EffectRunner 开始操作：再次检查许可、标记 started、将真实句柄绑定到执行槽。停止捕获 reserved 和 started 两种状态；reserved 被撤销后绝不能启动。句柄创建和绑定必须在同一受仲裁的启动片段中，不允许先启动一个异步网络/OS 操作再等待另一轮异步登记。控制锁内不等待操作完成；实际副作用的可取消性与结果核对仍由适配器负责。进程在 started 与实际调用之间崩溃也按不确定操作核对，不盲目重放。

- 内部消息提交：许可检查、额度占用、outbox 提交在同一控制事务中，明确属于停止前或停止后。
- 文件写入、Shell、外部 API：记录准入后执行，并持有可取消或可核对句柄。每个后续独立写操作重新核对许可。
- 第三方 Promise 忽略 abort：`Promise.race` 返回不表示底层副作用已经消失。迟到结果不能再写消息、继续调工具或提交记忆；实际在途操作需单独登记。
- 超过可配置等待时间（首版建议 5 秒）仍未收束：报告“已阻止继续执行，仍有操作结束中”，列出可核对项，不写“全部停完”。
- 取消后可继续写取消/工具实际结果审计记录，但不能发布已失效的普通助手正文。

新用户命令可以受理，但仍在途的旧副作用持有资源占用。新任务不能与它同时写同一文件、管理同一资源或提交冲突操作；等待旧句柄收束或由用户明确处理不确定结果。资源范围无法证明不冲突时，至少阻止该主体的新写操作，状态为 waiting/needs_attention，不以 generation 已更新为理由放行。可证明独立的只读操作不必一起阻塞。普通 SendToAgent 不提供跨主体工作区隔离；多个主体写同一资源也必须经过共享资源冲突检查，不能仅做主体内锁。

### 7.5 两种竞态的处理

**claim 已完成，模型尚未开始时停止**：inbox 租约只证明领取权，不证明执行权。进入模型前再验证 ticket；无效则 held，不调用模型，不增加失败重试次数。

**投递与停止同时发生**：若发送事务先提交，保留已发送回执；若停止事务先提交，拒绝旧 ticket 的投递。不能出现“先回已停止，随后旧 ticket 又获准发送”。

### 7.6 错误与重启

- 控制持久化失败：在进程内先关闭新的准入，报告停止状态无法持久保存，并尽力取消现有句柄；不能确认停止成功。重启时损坏控制存储禁止自动执行，提供诊断。
- 写失败但旧快照仍完好的情形也不能声称重启会记住此次停止。尽力写独立故障标记；启动恢复在异常退出或存在未收束票据时默认核对、禁止自动重跑。若磁盘完全不可写，明确告知尚无持久停止保证，需要保持服务关闭或人工处理；不能依赖一定可写成功的备用文件作绝对保证。
- 生效点后进程退出：恢复时先加载控制状态，再恢复投影和租约，最后才启动调度器。
- 旧 processEpoch 的许可不能复用。`stopping` 记录重建后核对未完成副作用，再给出终态。
- 重复 stop 返回同一 stopId 和结果；不重复增加 generation，不重复发送停止确认消息。

## 8. 收件箱与回合终止

### 8.1 消息状态与执行处置分离

保留原投递处理状态，增加独立的执行处置，避免暂停被当成网络错误重试。

```ts
interface DeliveryExecutionState {
  status: 'pending' | 'claimed' | 'handled' | 'failed';
  disposition: 'eligible' | 'held' | 'cancelled';
  holdReason?:
    | 'agent_paused' | 'chain_paused' | 'budget_exhausted'
    | 'manual_review' | 'legacy_unscoped';
  activationTicketId?: string;
  inputId: string; // 稳定 deliveryId
  chainId: string;
}
```

处置字段可保存为 inbox 投影，但是否允许执行仍以 `RuntimeControlStore` 为准。控制已经暂停、inbox 的 held 标记还未补齐时，也不能开跑。

调度器的 `nextWakeAt` 必须排除不可执行的 held/cancelled 项。暂停状态等控制事件唤醒调度器，不以 100ms 定时轮询不断重试被拒绝的同一项。

### 8.2 领取、许可与终态的跨文件协议

同一主体的 claim、renew、reclaim、ack 和准入通过同一仲裁器串行处理；不能一处直接写 inbox 租约、另一处独立核对后签票。固定锁顺序为主体仲裁 → 控制事务或单个投影写入，持有投影锁时不得反向申请主体/控制锁。

1. 领取消息得到持久 `deliveryId + leaseOwner + leaseEpoch`；签发 ticket 时绑定这组身份，并在相同主体仲裁内确认租约仍当前。
2. 控制票据持久提交后才能启动模型；启动时复检租约和 ticket。换手先撤销旧许可，递增 lease epoch，再签新许可，不能两个消费者同时取得可写许可。
3. claim 成功但 ticket 未提交即崩溃：此时没有模型/工具副作用；恢复按租约及控制 gate 重新判断，不因 claimed 就直接启动。
4. 业务终态先写控制事实源，再按稳定 ticket/input 身份幂等投影 inbox ack/disposition。终态已提交、ack 未写时崩溃，恢复只补 ack；不能看到 inbox 仍 pending/claimed 就重跑。
5. 只有实际执行是否完成尚无法确认时，才进入副作用核对。查到权威完成事实不重新执行，查不到也不能当成肯定未执行。

`inbox` 的租约是并发领取事实，控制存储是准入与执行终态事实；两者之间靠上述提交顺序和恢复规则，而不是假设多个 JSON 原子提交。

### 8.3 回合结果不能等价于“函数没有抛异常”

统一内部结果，兼容投影到现有 `ChatRunStatus`：

| 内部结果 | 用户直接回合 | 同事/群回合 | inbox 后果 |
| --- | --- | --- | --- |
| `completed` | 已回答/明确完成 | 已处理，有必要的出口 | handled |
| `silent` | 不允许直接当用户任务成功 | 合法不回应，不自动补发给主人 | handled |
| `blocked` | 交付实际阻塞及已执行事实 | 原因可查，必要时才通知主人 | held/manual_review，不自动重复 |
| `cancelled` | 显示该范围已取消 | 不发布普通正文 | 未处理部分 held/cancelled，保留副作用证据 |
| `failed_retryable` | 明确失败 | 仅安全无副作用时退避 | 有限重试 |
| `failed_terminal` | 明确失败 | 不重复执行 | failed |
| `incomplete` | 显示完成项和未完成项 | 记录未完成，不自动当成新任务 | held/manual_review |

`handled` 只表示来信已经被处理，不保证对方请求的业务成功。收件状态和业务结果分别显示。

`InboxProcessor` 必须查看结果类型，不能遇到返回 `cancelled/incomplete` 仍无条件 ack 为成功，也不能统一 nack 后定时复活。

### 8.4 出口和普通文本

- 所有用户可见文本统一经过 `ReplyFinalizer`。
- `SendToUser` 是明确用户/群出口；`end_turn=true` 结束该回合，不结束独立同事。
- 直接用户私聊的纯文本最终答复可保留兼容兜底，但必须走相同核验与持久出口。
- 同事和群回合没有明确出口时允许 silent，普通收尾草稿不自动发给主人。
- 同事信已经成功回复后，没有更多动作即可结束；运行时不得因缺少群回执强制继续调用。
- 错误结果、无新增进展和到达预算必须有确定的收尾路径，不能依赖模型自己“懂得停”。

## 9. “防止假装已发群”的修复设计

### 9.1 完整拆除旧完成门

必须一起替换以下逻辑，不能只改其中一处：

1. `requiredDeliveryFrom(text)` 的全文关键词推断。
2. `RunExecutor` 对所有非群文本注入 `requiredDelivery`。
3. `deliveryRequirementSatisfied` 仅比较 `kind`。
4. `SendToUser` 在没有成功群投递时拒绝普通回答。
5. `AgentLoop` 反复要求“必须调用 SendToAgent”，并在三次后笼统报“消息尚未发送”。

来源标签检查改为展示层的元数据信任边界。正文中的 `[发言于…]` 可作为普通引用文本处理，不因此制造外发义务。平台“消息来自/发言于”条目必须由真实消息字段产生。

### 9.2 真实回执

```ts
interface DeliveryReceipt {
  receiptId: string;
  actionId: string;
  inputId: string;
  chainId: string;
  actorId: string;
  target: { kind: 'agent' | 'room'; id: string; nameAtSend: string };
  payloadHash: string;
  outcome: 'accepted';
  committedSeq: number;
  acceptedAt: number;
  deliveryId?: string;
  timelineMessageId?: string;
  recipientDeliveryIds?: string[];
}

type DeliverySubmitResult =
  | { kind: 'accepted'; receipt: DeliveryReceipt;
      projectionStatus: 'pending' | 'visible' | 'failed' }
  | { kind: 'rejected'; attemptId: string; actionId?: string; code: string }
  | { kind: 'unknown'; actionId: string; code: 'DELIVERY_COMMIT_UNKNOWN' };

interface DeliveryAttemptRecord {
  attemptId: string;
  actionId?: string;
  observedResult: DeliverySubmitResult['kind'];
  code?: string;
}
```

回执由投递服务在提交成功后产生，完整 payload 保存在受权限保护的 outbox/归档中，hash 仅用于匹配。不可变 `DeliveryReceipt` 只保存已提交事实；拒绝和暂时未知是调用尝试的观察结果，单独记账。unknown 之后查到 accepted 是获得了确定事实，不是把一份不可变“未知回执”改写成成功。

展示状态单独由事实派生：

- `accepted`：平台持久受理，已有稳定的投递事实。
- `visible`：对应时间线/往来投影已完成，可以定位原文。
- `queued/held/processing/handled/failed`：收件方处理情况。
- 收件人是否回复、是否完成业务：引用另外的消息/运行证据，不篡改原始发送回执。

UI 与工具不能把 accepted 描述成“已完成任务”。投影延迟时可显示“已受理，正在同步”；只有对应公开时间线可查询后，展示“已发到某群”。接收者仍暂停时显示已投递、待处理即可。

### 9.3 SendToUser 增加可验证引用

在既有参数上增加可选 `delivery_refs: string[]`，每轮最多 8 个 receiptId。保持老调用兼容。下面仅示意文本变体的新增字段，既有附件、widget、secret-request 等判别联合及路由规则继续保留，不能强制转换成纯文本参数。

```ts
interface VisibleReply {
  content: string;
  delivery_refs?: string[];
  end_turn?: boolean;
}
```

验证器必须检查：

- 回执存在且 outcome 为 accepted；
- 当前主体有权查看，且没有通过引用泄露别人的私聊；
- 发送者和动作范围有效；有结构化 intent 时进一步匹配具体 targetId 和 payloadHash，否则只从回执读取真实目标/正文，不凭 refs 推断整段答复说了什么；
- 本次确认使用本次输入或显式恢复动作的回执；历史回执只能标为历史证据；
- 不能以给张三的私信证明已向牌局群发言；不能以同群的另一条消息证明本条发送成功。

平台根据回执生成独立状态条：真实收件方、时间、原文预览/跳转。这些字段只能取自回执及投影，不允许模型正文覆盖。引用只是相关动作的证据，不给整段自由文本中的所有陈述背书。有效甲群回执绝不能生成乙群成功条目；正文是否谎称乙群仍需有限语义核查，不能因为 refs 有效就把整段文本标为 verified。

引用无效时返回结构化 `INVALID_DELIVERY_REFERENCE`，允许一次仅修正回答的机会；不重新进入无限工具循环，更不能为了让引用有效而自动发一条消息。

### 9.4 原始自然语言请求的处理

原始用户聊天没有可靠的结构化动作清单，不能假装任意一句中文都能被确定性解析成一个硬约束。

本方案区分两类输入：

| 输入来源 | 如何描述待办动作 | 允许做什么 |
| --- | --- | --- |
| 结构化发送入口：用户明确选定目标和正文 | `DeliveryIntent` 绑定 commandId、真实 targetId、payloadHash | 按现有权限执行，最终以对应回执判结果 |
| 自然语言对话 | 模型形成执行计划；平台只作有限的意图/声明核查 | 不能仅凭关键词创建硬门；不能从同事正文获得用户控制权限 |

自然语言核查可以识别“遗漏了用户要求的发送”，但只能影响结果说明和任务状态，不能授权未经实际发送工具的投递。

结构化 `DeliveryIntent` 字段建议：`intentId, commandId, actorId, targetId/type, payloadHash, actionId?, provenance='user_command'`。目标或正文尚未确定时，状态为 unresolved，不能冒充已验证目标。

### 9.5 有限声明核查与纠正

将“逐条发言验证”和“执行进入最终收尾”分开。所有出口经过相同事实检查，但普通 `end_turn=false` 的合法进度发言不改变执行阶段；只在最终答复、硬预算、无进展或确需终止纠正时进入单向 Finalizing。

明确的投递完成声明走以下流程，包括 `SendToUser` 和私聊最终正文兼容出口：

1. 先验证 `delivery_refs` 或当前动作的结构化结果。确定性通过只批准相应事实状态条，不自动批准整段自由正文。
2. 若自由正文含待核对的发送声明，运行一次只读核查，即使它附有有效 refs 也不能跳过目标/内容矛盾检查。核查只访问当前输入、候选答复、当前主体可见的候选回执及必要目标元数据。
3. 核查结果为 `supported / contradicted / unverified / not_a_delivery_claim`，附具体目标和证据 ID；supported 是有证据支持的语义判断，不是自由正文全部真实的机械证明，不能生成新的发送动作。
4. `contradicted`：不发布错误的成功确认，使用实际已提交事实生成简短纠正；若用户要求的动作未完成，结果为 incomplete/blocked。
5. `unverified`：不得显示成功徽标。对具体发送声明给出“未找到可核对的发送记录/结果待核对”，不要把所有正常聊天都标上未验证。
6. 最多允许一次仅修正文案的模型调用；无写工具、无发送工具。需要纠正未完成的成功声明、仍不合规或核查超时时，转入 Finalizing，运行时交付保守说明并结束，不回到普通执行循环。

首版核查可使用现有模型的结构化响应，预算建议：输入最多 8,000 字符、输出最多 1,000 字符、10 秒超时、每回合最多一次核查和一次修正。精确回执验证是本地代码；模型核查只做自然语言归因，不是事实源。固定核查提示放单独模块，稳定复用，不注入每轮主系统提示的大段补丁。

正常进度消息验证通过后仍可继续执行必要工具；结构化发送请求尚在执行中，不能因为中途进度消息尚无最终回执就判“遗漏发送”。**进入 Finalizing 后**，`AgentLoop` 只允许走向完成、未完成、取消，不再执行业务工具；只允许平台提交一次已核对的收尾说明。系统取消优先，不等待核查这 10 秒。

每回合语义核查额度不因中途发言增加：已用完额度后，再次出现需要语义背书的发送确认，只显示可核对的规范化状态条，不发布无法判断的成功断言。普通聊天/进度无需一律触发模型核查。业务工具重复、纠正回答和核查各自计数，不能互相重置预算。

核查触发可用低成本语义分类或候选扫描；扫描只能决定是否检查，不能直接创建外发义务。分类器漏判仍可能放过错误自由文本，因此必须在交付说明中承认：**平台能机械保证真实回执和来源条目不被伪造，不能机械保证任意自由文本全部真实。** 不能把语义模型当成新的绝对真值门。

如果产品未来要求绝对禁止任何未经证明的发送确认，则该类确认必须只用结构化回执模板表达，并接受对自由文本表达能力的限制；不要声称当前兼容聊天模式已经提供此保证。

### 9.6 禁止出现的“修法”

- 增加“发牌员”“斗地主”等排除词，把本次语料硬编码进规则。
- 将所有“群 + 发”改成“群 + 说”，继续全文拼词。
- 成功发给任何一个群就通过所有投递完成检查。
- 给普通失败说明增加额外授权要求，或要求先调用一个必然失败的发送。
- 在纠正模型虚假声明时，系统偷偷补发消息使声明变真。
- 仅移除红色错误展示，仍然让内部循环继续发送。

## 10. 投递提交、投影和幂等

### 10.1 动作身份由运行时分配

动作索引的作用域为：`actorId + inputId + logicalAction`。默认投递指纹包含：

```text
实际 actorId
+ 解析完成的 target.kind / target.id
+ 原样语义 payload 的 hash（正文、附件 URL/标识、必要发送属性）
```

同一输入下相同指纹映射到同一持久 actionId。不同 `callId`、JSON 参数键顺序、名字别名和 runId 不能绕过去重。payload 的正文空格、标点和换行不能随意压缩，参数对象的键序可规范化。

新用户命令有新的 inputId，因此用户再次明确发送同一句话仍能产生新消息。不能在整个项目上永久按“目标 + 正文”去重。

模型不能任意指定新的 actionId。若同一输入确实要求重复发送同文多次，必须来自该输入的明确动作序号/用户重发控制，不接受模型自行变更一个 nonce 绕过保护。首版默认抑制同输入同目标同 payload 的重复发送。

文本变了一点可能产生新指纹，哈希不能识别全部语义重复；这类放大由链预算和无进展收敛共同限制。

### 10.2 本地事务时序

1. 在调用者可见范围内查稳定动作索引；已提交的同动作先返回原事实，不以当前主体已暂停或目标后来被删为由抹掉它。查事实不授予新执行权。
2. 对尚未提交的新动作，解析真实目标及调用者权限，获取群成员快照和元数据版本。
3. 进入控制事务，复查动作索引、ticket、目标版本、链状态和剩余额度；并发已提交则返回原回执，不扣额度，不调用 enqueue。
4. 否则分配固定 actionId、receiptId、deliveryId、roomMessageId 及每个成员的 deliveryId。
5. 在同一个控制快照中写入完整 committed outbox、不可变回执和额度占用。
6. 提交后调度投影：按确定 ID 写群时间线、correspondence、每个目标 inbox。工具可等待一次有界的本地快速投影，也可直接返回 accepted/pending，不等待后台修复完成。
7. 对具备消费所需投影的目标发调度通知。任何一步均不等待收件模型；提交后即使 projector 抛错，工具结果仍是 accepted，并附 pending/failed 投影状态，不能被通用工具异常包装改成“发送失败”。

目标版本校验必须与群/注册表修改使用同一元数据仲裁入口；不能在事务前读一次成员表，随后成员被移除仍用旧权限批准新发送。首版所有主体/群元数据写入口均接入 RegistryCoordinator；固定顺序为所需主体/元数据仲裁 → 控制事务 → 退出控制事务后投影。需要多个主体锁时按稳定 ID 排序，投影写锁内不反向申请仲裁或控制锁。元数据版本在持有仲裁期间保持不变；不允许有绕过入口的直接修改。模型、网络和消费者不持有这些锁。

只对已提交 outbox 做投影。投影失败后可重试投影本身，不调用 LLM，不重新解析目标，不再扣预算。

### 10.3 投影接口必须具备幂等性

需要新增或扩展：

- `inbox.putIfAbsent(deliveryId, item)`；
- `roomTimeline.appendIfAbsent(roomMessageId, message)`；
- `correspondence.putIfAbsent(deliveryId, record)`；
- 回执/动作查询按 actionId、receiptId 返回固定事实；
- 同 ID 不同 payload 必须报一致性错误，不能静默覆盖。

现在的随机 `inbox.insert` 和普通 JSONL append 不能直接承担这些保证。每个投影都要有重启后可恢复的 ID 索引。

收件箱可消费前需确认 outbox committed，且该收件人的必要历史/时间线已存在。群其他成员投影失败不应阻止已经准备好的成员永远运行，但发送状态要如实保留待同步成员。

### 10.4 崩溃窗口

| 崩溃点 | 恢复行为 |
| --- | --- |
| 控制事务提交前 | 没有发送事实，无下游可见副作用；同动作可重新尝试 |
| 提交后、任何投影前 | 读取 committed outbox，按固定 ID 补投影，不重跑模型 |
| 群时间线写完、部分 inbox 未写 | 保留同一公开消息，补剩余成员投递；不重新取当前成员全体扇出 |
| 投影完成、调用方未收到返回 | 查 actionId，返回原回执，不创建第二封信 |
| 下游工具产生副作用后、来信未 ack | 沿用保守副作用核对，进入需核对；投递幂等不等于下游业务幂等 |

调用结果 `unknown` 表示提交结果暂时无法确认；优先查权威动作记录。查询存储失败时也不能换一个新 actionId 重发。已查明 committed 后始终返回原 accepted 回执；投影失败、暂停或目标删除只改变后续处理状态，不推翻已受理事实。

### 10.5 群边界

- 发往其他群：提交一条公开消息及目标成员快照，成员独立消费。
- 当前群 `SendToUser`：公开消息同样通过投递提交服务，只有真实新 `@` 对象按既有配额派生新投递，不能全员重扇出。
- 成员加入：不补发加入之前消息。
- 成员退出/被删除：消费前复查，取消其未执行投递，保留消息已发送事实并记录跳过原因。
- 1:1 图片继续支持，群纯文本规则保留。
- 对发送者暂停而言，停止之前已提交的消息可继续完成本地投影，并由独立收件人处理。它不是停止之后新获准的发送。

## 11. 收敛：统一错误、重复动作和链预算

### 11.1 统一错误分类

所有工具校验都由统一执行包装层产生结构化结果，包括 tool 参数校验阶段；不要只在 `dispatch` 的 try/catch 内登记失败。

| code | 是否自动重试 | 收尾策略 |
| --- | --- | --- |
| `TARGET_NOT_FOUND` / `TARGET_AMBIGUOUS` | 否，除非参数被实质修正 | 说明具体目标问题 |
| `NOT_ROOM_MEMBER` / `UNAUTHORIZED_ACTION` | 否 | 说明权限/成员范围 |
| `INVALID_ARGUMENTS` / `INVALID_IMAGE` | 仅有意义地修正参数 | 有界修正，普通解释始终允许 |
| `CHAIN_DEPTH_EXCEEDED` / `CHAIN_BUDGET_EXHAUSTED` | 否 | 结束协作动作，标阻塞/预算暂停 |
| `AGENT_PAUSED` / `STALE_ACTIVATION` / `CANCELLED` | 否 | 撤销执行，不调用模型继续劝它外发 |
| `DELIVERY_COMMIT_UNKNOWN` | 不得盲目重发 | 查询原 actionId |
| `STORAGE_TEMPORARY` | 仅无不确定副作用的操作 | 使用同一动作身份退避 |
| `DUPLICATE_ACCEPTED` | 已成功，不是错误 | 返回原回执并收敛 |

`SendToUser` 的普通说明不依赖 `hasFailedDeliveryAttempt`。在取消状态下，只有平台停止结果可以发布；不能借“允许说明”让旧 ticket 继续写普通消息。

### 11.2 无进展收敛

- 同一动作已经 accepted 后又重复请求：返回原回执；重复不会算新的业务进展。
- 连续 3 次相同拒绝类别、同一目标/动作且没有状态变化：停止该动作的自动尝试，进入只总结阶段。
- 拒绝类别和动作身份由结构化字段判断，不用原始 arguments 字符串是否完全相同。
- 参数真的修正、目标重新解析成功等可算进展；仅改一句文案或 JSON 键顺序不重置。
- 达到单回合硬预算时只输出已完成事实和未完成项，不将“请继续”自动转发给同事。
- 原有文件工具输入输出限制继续有效，本设计不增加用量统计面板。

### 11.3 因果链预算

`chainId` 在用户根输入建立；来信、回信、群投递和真正的工人通知继承它。新 run、切频道、深度上限报错都不能新建根链。

首版建议配置，数值是可调产品额度，不是提示词要求：

| 配置 | 初始建议 | 计数规则 |
| --- | --- | --- |
| `maxAutomaticRunsPerChain` | 24 | 每次成功准入自动回合原子计数，安全重试也计实际执行次数 |
| `maxDeliveryActionsPerChain` | 24 | 每个新 accepted 投递动作一次；重复回执不加 |
| `maxRecipientDeliveriesPerChain` | 48 | 群发每个接收成员分别占用，DM 占 1 |
| `maxAgentChainDepth` | 保留当前默认 | 跨 DM/群继承，不通过换群清零 |
| `maxRepeatedNoProgress` | 3 | 同动作拒绝/重复无进展阈值 |

这些值必须支持配置及小预算测试。大项目需要更高额度时，调整明确任务范围的配置；不能通过无限后台对话规避预算。真正长时间执行的工具工人仍使用自己的时间/工具预算，不等于给聊天来回无限额度。

额度占用与投递/准入的提交放同一控制事务；ack、删除队列项、程序重启不退回已消耗计数。取消了未提交的预留才可释放。

到顶处理：持久设置链为 `paused_budget`，后续自动激活 held；给相关主人界面一条结构化摘要。不能为通知预算耗尽再广播一轮同事消息。用户明确继续该链可以增加额度，不把旧计数清零。

这里暂停因果链是平台运行额度约束，不代表某个同事拥有其他同事的任务取消权。

## 12. 创建智能体和建群的配套修复

创建三人和建群的请求应由正常工作台动作完成，不需要靠给同事发“继续”绕过每回合上限。

### 12.1 配额归属

- 移除 `MAX_AGENTS_PER_TURN=2` 作为面向用户的批量创建硬门。
- 采用 `WorkbenchActionScope`：绑定可信用户 inputId/chainId、创建计数、允许操作类型和资源上限。
- scope 至少含 `issuedByCommandId, authorizedActorIds, operationTypes, resourceBounds, delegationPolicy, consumedQuota`。由可信请求入口或受约束的工作台计划签发给实际负责主体；普通同事消息不能签发，chainId 只用于关联，不是管理授权。
- 首版允许当前明确的三人创建请求；建议一般创建上限默认为每用户请求 6 个，超过时明确说明产品限制。群成员上限继续独立校验。
- 同一工作台请求的续跑、传话或工人不能重置额度。只给另一人发消息，不代表它获得新的用户创建额度。
- 创建权限继承和工具可用性仍遵守已有 `ExecutionAuthority`。不要为了修这次循环，粗暴撤掉所有同事的管理工具。

“有 CreateAgent 工具”只是必要条件，不代表拥有这次请求的工作台 scope。扩大 authorizedActorIds 必须符合原 scope 的明确委派策略和执行权限；如确有授权委派，所有主体共用原额度，不增加资源上限。无法从可信请求确定是否包含管理操作时，不能仅因模型提出一个计划就授予管理范围。

不采用新的中文数量正则作为硬授权解析器。用户显式工作台 UI 可直接签发结构化范围；自然语言动作由规划层提出并绑定原请求，遇到不确定范围只暂停相关写操作并说明，不能强迫外发。

### 12.2 幂等与部分成功

- `CreateAgent/CreateChannel/UpdateChannel` 使用动作身份和稳定结果记录。创建前先在控制事务提交固定 resourceId、payload、scope、额度占用和待执行 mutation；注册表只接受 `createIfAbsent(resourceId, payload)`，同 ID 不同内容报错。
- 同一创建动作重试返回已创建资源，不能仅按名字猜它是不是本次创建的。
- 资源写入成功、控制结果尚未回填即崩溃时，恢复查询原 resourceId，补结果而不创建第二份。UpdateChannel 使用 expectedRevision 和 appliedActionId；已应用动作重放返回原结果，旧版本更新不得覆盖后续成员修改。
- 待执行工作台 mutation 不等同于已经提交的消息 outbox：mutation 仍需有效 EffectPermit 才能实际写资源。停止前预留、未开始的 mutation 取消；已经执行但未回填结果的 mutation 只核对，不能因为恢复投影而新增管理副作用。
- 不同请求遇到同名资源继续消歧，不自动覆盖。
- 部分成功时返回真实的已建列表和未完成列表，不自动删除已建资源。
- 建群前核对目标成员的实际 ID；缺成员时标为部分完成，不宣称“全建好了”。

工作台权限模型的进一步细分可以单独迭代，但此次必须修复配额冲突、重复创建风险和阻塞无法报告。

## 13. UI、事件与可观察性

### 13.1 展示类型

建议从统一事件事实生成以下视图，而不是所有消息都塞进一个文本气泡：

| 视图 | 内容来源 | 展示位置 |
| --- | --- | --- |
| `ChatText` | 明确用户/助手可见正文 | 普通聊天 |
| `Correspondence` | 真实双方身份及 deliveryId | “消息来自/已发给”及往来查看 |
| `DeliveryStatus` | 平台回执及投影状态 | 收件方、发送状态、原文定位 |
| `ExecutionActivity` | tool_calls/results、运行状态 | 执行面板 |
| `ControlNotice` | 停止、暂停、预算、未完成事实 | 范围明确的系统状态条 |

首版可保留现有 `DisplayMessage` 数据结构，但必须有统一 `isChatRenderable` 选择器供历史和 SSE 使用。纯工具消息留在数据中供执行面板读取，不能在 `MessageItem` 外层产生头像、时间、空泡及复制按钮。

correspondence 的空 content 不应被普通 `trim()` 过滤误删；按展示类型判断。含附件/选项卡的消息也不能按是否有文字粗暴过滤。

### 13.2 停止展示

- 命令受理：显示正在停止及作用范围。
- 控制生效但句柄未结束：显示已暂停后续自动处理、仍有操作结束中。
- 真正收束：显示该智能体已停止，旧来信待处理。
- 独立同事继续运行时可以在其状态中看到，不把“停止当前智能体”描述成所有人已停。
- 暂停成员在群里显示暂停/待处理，不记成模型主动沉默。

一次 stop 用稳定 stopId 更新同一状态条，不追加“在停/停完了”的重复助手对白。

### 13.3 快照和事件

在 `ChatSnapshot` 增加受权限约束的 `agentControls`、活动 stop 状态、held 数量、必要回执视图；在 SSE 增加控制/投递事件。扩展 `JournalEntry.kind`、服务端路由及客户端 reducer，避免前端默默忽略新类型。

`controlSeq` 负责控制提交顺序，SSE `epoch+seq` 负责观察顺序，不混用。快照按现有重读/游标规则生成，重复和乱序事件不能解除 paused，也不能将终态变回 running。

原始异常码放执行详情。用户状态说明应反映“目标未找到”“投递结果待核对”“本轮额度用尽”等事实，不能对已经发出三遍的私信显示笼统“消息尚未发送”。

### 13.4 最小诊断字段

所有运行/投递审计保留：`commandId, taskId, runId, inputId, chainId, actionId, receiptId, actorId, targetId, generation, admittedSeq, committedSeq, outcomeCode`。

诊断面板能够回答：由哪条消息叫醒、凭哪份许可、为什么允许/暂停、发给谁、是否重复、停止覆盖了哪些执行。正常聊天不逐条解释这些内部字段。

## 14. 提示词调整原则

将主提示中的出口规则与真实运行时行为对齐，只表达行为约定。下面是建议的通用约束，不加入本次人名、牌局或具体误判语句：

> 对用户或当前群的可见发言通过指定出口发送。给同事或其他群发消息后不等待对方回复。只有真实投递回执可以支持发送完成的确认；失败或结果未知时如实说明。没有需要回应的新信息可以结束同事回合，不重复确认或转述。当前任务的阻塞不构成另外发送消息、创建资源或续做旧任务的理由。

提示词不得承诺“普通正文永远不交付”而代码又无条件兜底；私聊兼容兜底与同事/群沉默策略以第 8 节为准。

系统状态、控制代次、租约和幂等不交给模型维护。主提示不增加一长段“遇到某句话就怎样”的修补规则。

## 15. API 与兼容入口

新增接口以下为目标契约，当前尚不存在：

| 接口 | 用途 | 约束 |
| --- | --- | --- |
| `POST /api/agents/:id/stop` | 停止当前智能体 | body 含 commandId；202 返回 stopId/生效状态，完成走事件 |
| `GET /api/control/stops/:stopId` | 查询停止进度 | 返回真实在途项及作用范围 |
| `POST /api/agents/:id/resume` | 恢复选定任务/来信/链 | 显式目标 ID，检查原动作副作用，不全量 drain |
| `GET /api/agents/:id/control` | 查询暂停、held 和可恢复项 | 只读 |
| `GET /api/deliveries/:receiptId` | 查询回执及可见原文 | 验证可见范围，不能跨智能体偷读私信 |
| `POST /api/control/stop-all` | 可选的用户全局停止 | 只有完整实现 all_agents scope 后开放；E4.4 复核后仍不做（理由见 `docs/架构设计.md` §7.1），当前如实返回 `UNSUPPORTED_STOP_SCOPE` |

现有 `/api/chat`、`/api/sessions/:id/messages`、`/api/agents/:id/messages` 的停止词都转发到同一控制命令处理器。不能每个路由实现不同的停止。

现有 `POST /api/agents/:id/inbox` 只是请求处理，不能绕过暂停；暂停时返回 held 原因。`/inbox/retry` 的重试需改为可选定投递，不能顺便恢复已停止协作。

`resumeTaskId` 的旧语义要做显式适配：区分 taskId 和旧实现里实际传入的 run/checkpoint ID。找不到唯一映射时报错，不能恢复“最新一个看起来失败的任务”。

新字段是可选兼容读取，但新控制写入只有一套规则。HTTP 不接受模型伪造的 sender、generation、chain 根来源或控制 grant。

## 17. 迁移、上线与回退

### 17.1 实施前

1. 检查工作区未提交更改，保留用户已有代码。
2. 在服务停止或取得现有单实例锁后，备份 `.agentbot`；记录备份路径、schemaVersion 和校验摘要。
3. 使用独立测试目录验证迁移，不直接拿真实消息触发新模型执行。

### 17.2 迁移步骤

1. 新运行时先不启动 scheduler、resume 或 inbox drain。
2. 建立 versioned 控制存储，迁移 checkpoint 与原始输入身份的可证映射。
3. 新建智能体默认 enabled。此次升级的已有智能体默认暂停自动激活，标记 migration_review，防止旧积压再次制造风暴；界面说明是升级待核对，不假称用户曾下过停止令。
4. 旧 pending/claimed 来信按证据恢复为 held。已取消树、无法确认副作用或因果身份不完整的项不得自动重跑。
5. 旧 `tool_calls` 和错误消息保留历史，调整展示投影；不批量删除对话和记忆。
6. 旧成功发送如果只有文本结果、缺少可验证目的地/消息关系，不伪造 v2 回执；标为 legacy/unverified，禁止把恢复视为可安全重发。
7. 用户可明确选择需要恢复的主体和旧事项。新用户输入可以正常开始新链，无须恢复全部旧积压。
8. 迁移完成标记最后提交。重复运行迁移应得到相同 ID 和处置结果。

旧数据不能仅因在“停止”之后创建了新的 run 就认定是新授权任务。优先使用用户命令来源和消息关联；无法证明时 held，不猜测。

### 17.3 开关与部署

可以分阶段合并代码，但 v2 writer 上线后必须只有一个发送和激活路径。禁止旧 scheduler 与新 coordinator 同时给票据，禁止双写两份权威收件箱。

建议只提供一个运行控制版本开关用于部署切换，而非让用户组合“旧停止+新投递”等未经验证的混合协议。

### 17.4 回退

新 schema 产生数据后，旧版本不得自动消费 v2 outbox 或忽略暂停字段启动。回退必须先停止服务，使用一致备份恢复到对应版本，或保持只读直到完成兼容转换。

备份恢复不会撤销已经真实发送、创建或执行的外部副作用；回退前核对已提交动作，不通过重放旧请求补齐未知结果。

## 18. 验收测试矩阵

测试应使用 FakeProvider、独立 tempDataDir、可控制的 deferred Promise、假时钟和提交故障注入。不要依赖真实模型“碰巧没回话”或固定 sleep 判断并发正确性。

### 18.1 停止和恢复（A）

| ID | 场景 | 必须断言 |
| --- | --- | --- |
| A01 | 用户回合正在模型调用，用户停止 | 立即撤销许可并 abort，不等模型自然完成 |
| A02 | stop 前存在多封旧积压 | 停止确认后模型调用计数不再增长，旧信仍可查 |
| A03 | 已 claim、未开始模型时 stop | 不调用模型；归 held；失败计数不增加 |
| A04 | 工具准入/提交与 stop 并发 | 提交序号严格决定是否允许；旧票据不能穿透 |
| A05 | stop 后迟到的旧链回信 | 归档成功、不自动唤醒 |
| A06 | stop 后用户新任务 | 新链执行；旧信不释放；新链合法回信可按 grant 执行 |
| A07 | stop 与新用户命令同毫秒 | 以 controlSeq 为准，新命令不被误取消 |
| A08 | 同 commandId 重复 stop | 相同 stopId；generation 只递增一次；一条控制状态 |
| A09 | stop 提交后立即崩溃 | 重启旧工作仍暂停，旧 processEpoch 无效 |
| A10 | 持久写失败或底层句柄不结束，再受理新任务 | 不显示完全停止；新任务不得与未结束旧操作写同一资源；未知范围不放行新写操作 |
| A11 | 独立张三继续执行并回信 | 张三不被本地 stop 级联取消；已暂停发送方不因旧链回信复活 |
| A12 | Task 工人执行中 stop | 取消真正拥有的工人，无新增副作用 |
| A13 | finally、启动恢复、手动 drain、群 @ | 全部经过相同 gate，不可绕过 |
| A14 | 用户仅开启未来自动处理，随后旧链迟到回信 | 旧 held 项仍 held；此前尚未到达的旧链来信也不启动 |
| A15 | 只恢复一封旧信/一个任务 | 同链其他未选来信及其他旧事项不启动；原动作身份保留 |
| A16 | 已提交消息的投影在 stop 后完成 | 仍显示原已发送事实；无新的 actionId |
| A17 | 主人新私聊甲，甲联系已暂停的乙 | 甲的新链可执行；乙不得凭链继承获得许可；真实用户选定的群受众另测有效 grant |
| A18 | claim→ticket、终态→ack 两个窗口崩溃及租约换手 | 无双消费者有效票据；无模型先于准入；已完成只补 ack，不重跑 |
| A19 | effect 已 reserved，尚未创建底层句柄时 stop | 预留被取消，工具不得启动；started 句柄必须可追踪和等待 |
| A20 | 快照到达新增 payload 软阈值 | 新增动作被拒，但停止与终态可提交；实际磁盘写失败不假报持久成功 |

### 18.2 真实投递与回答（B）

| ID | 场景 | 必须断言 |
| --- | --- | --- |
| B01 | 创建三个角色并建群的原始请求 | 不产生关键词群投递义务；创建结果可正常说明 |
| B02 | 同事索要 ID，正文顺带提到稍后建群 | 正确 DM 成功即可结束，不强迫发群 |
| B03 | 真正请求向指定群发送指定信息 | 成功回执必须匹配 actor、targetId、payload、动作范围 |
| B04 | 给甲群发成功，却声称发到了乙群 | 不得生成乙群成功状态或补发乙群；自由正文矛盾识别进入语义评估，不把有效甲群 refs 当全文真值 |
| B05 | 投递深度、图片、权限在 dispatch 前被拒 | 结构化拒绝存在；允许如实说明并终止 |
| B06 | 模型写平台来源前缀 | 不能生成来源组件、改变消息身份或触发新投递 |
| B07 | 候选正文谎称发送、没有回执 | 至多一次核查和一次纠正；外发计数不增加 |
| B08 | 普通问候、历史询问、引用他人发送经历 | 不创建发送义务，不被强迫重发；避免全聊天“未验证”噪音 |
| B09 | 有效但无关/过期动作的回执 | 不能当成本次动作完成证明 |
| B10 | 引用他人不可见私信回执 | 拒绝引用，不泄露原文 |
| B11 | 声明核查超时、输出格式错误、仍重复虚假声明 | 确定收尾，不回普通工具循环 |
| B12 | 用户要求发送却最终遗漏 | 对结构化 intent 确定标未完成；自然语言核查发现后明确未验证/未完成，不伪造成功 |
| B13 | 同事无须回应、群无补充信息 | 合法 silent，零条用户气泡，不因空正文报失败 |
| B14 | 直接用户请求失败 | 必须有可见结果说明，不能用 silent 当成功 |
| B15 | 已提交投递，回执返回丢失 | 查同 actionId 得到 accepted；不得说肯定没发 |
| B16 | 有效进度发送后仍有必要动作，end_turn=false | 逐条验证不提前终止；进入最终纠正后则不得再执行业务工具 |
| B17 | 附有效 refs 的自由正文、结构化事实条及非文本出口 | 事实条只读回执字段；refs 不使全文自动 verified；附件/交互保留既有协议 |

自然语言核查另做离线评估集：包含请求、否定、引用、历史、条件句、同名目标和多句混合。确定性单测验证有界流程与事实匹配；评估记录语义误判/漏判，不能把几个固定样例通过宣称为自然语言全面正确。

### 18.3 幂等、预算、故障恢复（C）

| ID | 场景 | 必须断言 |
| --- | --- | --- |
| C01 | 同输入同目标同内容串行重复三次 | 一个 action、一份回执、一封信 |
| C02 | 同动作并发两次调用 | 只提交一次，只扣一次预算 |
| C03 | 参数 JSON 键序变化、用名字再用 ID | 解析后仍同一动作 |
| C04 | 新用户命令发送相同内容 | 新动作允许发送，不被全局去重误杀 |
| C05 | 同来信的安全重试/恢复 | inputId/actionId 不变，不重复已提交副作用 |
| C06 | 同 ID 不同 payload | 一致性错误，不覆盖历史 |
| C07 | 提交前/后、时间线与 inbox 间分别崩溃 | 未提交不见；已提交只补投影；无重复群消息/新成员扇出 |
| C08 | 部分群投影失败，其他成功 | 故障可查，成功项不重发，剩余项幂等补齐 |
| C09 | 深度很小但同层不断换文案发送 | 总链额度限制膨胀，不能靠新 messageId 绕过 |
| C10 | 到预算后 ack、重启、续跑 | 计数不归零；不产生预算提醒的消息风暴 |
| C11 | 终态工具日志被裁剪 | 去重事实仍可用 |
| C12 | 创建三人后建群，过程重试 | 恰好三项创建结果，成员 ID 齐全，无绕过配额的派信 |
| C13 | 创建部分成功后暂停或失败 | 已建资源保留，结果准确，恢复不重建 |
| C14 | 同事有管理工具和相同 chainId，但无工作台 scope | 管理写操作被拒；不能凭普通来信获取主体授权或重置计数 |
| C15 | commit 成功、首次投影写失败，随后调用重试 | 工具仍返回 accepted+pending/failed；返回原回执，不重新发送；暂停/删目标不抹掉回执 |
| C16 | 资源已创建、动作结果回填前崩溃 | 查固定 resourceId 补结果，不创建重名副本；停止后未启动 mutation 不执行 |
| C17 | UpdateChannel 重放遇到更高注册表版本 | 已应用动作不重写；版本冲突不得覆盖新成员列表 |
| C18 | 明确授权委派工作台动作给另一主体 | 主体扩展受控，共享原额度及资源边界，工具可用性不代替 scope |

### 18.4 UI 与端到端（D）

| ID | 场景 | 必须断言 |

## 19. 实施顺序与交付检查

### 第一批：停止真正生效

交付控制契约、RuntimeControlStore、ActivationCoordinator、ticket fencing 和 agent stop；所有自动入口接线；新用户输入与旧协作隔离；补 A 类测试。

这一批必须能单独证明“停止确认以后，旧信不能让当前智能体再调用一次模型”。只修改 scheduler 的 paused 判断不算完成。

### 第二批：投递有事实、回合能结束

交付稳定 input/action/chain、DeliveryService、committed outbox、幂等投影与链预算；移除旧强制完成门；统一工具拒绝和内部回合结果；补 B/C 类测试。

这一批必须能证明“正确私信成功不会被要求另发群”和“达到深度上限能够结束”。

### 第三批：可验证回复与界面

交付 ReplyFinalizer、delivery_refs、有限只读核查、真实状态条、空泡过滤、控制快照和 UI；补 D 类测试。

### 第四批：工作台配套、迁移及交接

交付批量创建配额归属、幂等创建、迁移演练、崩溃恢复与回退说明；同步旧文档和提示词。

各批可以独立评审，但对真实用户开放 v2 前必须通过整条端到端验收。不要让半套新控制和半套旧发送协议混跑。

验证命令按当前 package.json：

```bash
npm run typecheck
node --test --import tsx test/preempt-stop.test.ts test/delivery-contract.test.ts test/collaboration-delivery.test.ts
npm test
npm run build:all
```

新测试文件加入正常测试集合。实现者应优先跑相关测试，全部修改收束后再跑完整测试和构建。原有测试中把“用户停止等待旧任务完成”作为正确行为的断言必须改掉。

最终交接必须附：

- 实际修改清单和新旧入口替换关系；
- A/B/C/D 每项用例对应的测试位置与结果；
- 真实链路测试：建三人建群→同事通信→用户停止→旧信到达→重启→新任务→只恢复选定事项；
- 同一 action 的提交/崩溃重试证据；
- 剩余不确定外部副作用、自然语言核查限制及配置值；
- 数据备份/迁移/回退方式，以及哪些旧回信仍待核对。

## 20. 完成定义

只有同时满足以下条件，才可称为本次修复完成：

1. 停止提交后，旧票据不再批准新的动作；停止确认与实际句柄收束一致。
2. 同一智能体不会被停止前积压信或旧链迟到回信自动复活。
3. 独立同事仍独立；真正的 Task 工人按所有权取消。
4. 直接新用户请求正常执行，旧协作不会顺带恢复。
5. 投递具有可查询的真实目标、payload、动作和回执，提交前后取消语义明确。
6. 同一动作重复调用不产生新信，跨轮预算能够阻止横向消息膨胀。
7. 普通失败说明和合法沉默能结束回合，不再出现必须外发才能说明外发失败的互锁。
8. 平台投递状态来自持久事实；无依据的完成声明有界纠正，不触发补发循环。
9. 三人创建与建群能在明确授权范围内完成，部分失败可交接、恢复不重复创建。
10. 历史加载、SSE 和重启恢复的 UI 一致，无工具空泡、身份冒充或错误的停止承诺。

本方案不以调整提示词措辞或单次人工演示成功作为验收。需要证明上述状态约束在并发、失败、重试和重启之后仍成立。
