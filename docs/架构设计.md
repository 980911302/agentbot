## 0. 当前行为与应保留的约束

### 0.1 身份、消息与记忆

- 每个同事有稳定 agentId；名字、职责、工具配置保存到注册表，每轮重新装配。
- 私聊、所参与群的入站内容、同事来信写进这个同事的经历；切换界面或话题不新建身份。
- 记忆分 self（自己的）、user（共用用户信息）、project（参加项目的），不能读取别人的 self。
- 记忆分 portrait/log/scratch 三层；画像溢出降级，日志和随手有容量清理，随手过期。被容量清理的条目不保证仍可检索，不能承诺永久完整记忆。
- 去重保留数字差异，项目写入显式定位项目；上下文由身份、记忆、检索、摘要和近期原文重组。工具调用与结果作为原子组裁剪。
- 记忆抽取和摘要都是有损处理；原始消息当前仍单独存档。新增可靠工作状态后，记忆不能成为工作终态的唯一依据。

### 0.2 群与同事协作

- 群只有名称、成员表、共享时间线和可选的运行模式（`open` 默认 / `managed` 受控流程）；不是中心 AI，也不是共享私聊记忆库。
- 成员上限当前 6，至少保留 1 位；不嵌套群；新成员不自动获得进群前全部记录。
- 点名按长名优先解析；@everyone 支持全员；无法解析的文本保持普通正文。点名语义只约束 `open` 模式。
- HTTP 和 SendToAgent 群入口统一先入队；`open` 模式下成员由 InboxScheduler 在空闲时独立唤醒，不保证同波成员看见彼此发言。进程内兼容入口 postToRoom 保留三波等待策略，但不暴露给 HTTP/模型工具。每成员每 roundId 最多被投递 2 次，已确认投递也计入持久配额。
- `managed` 模式下 `RoomFlowRouter` 接管：公开消息仍写时间线，但默认 `wakePolicy: none`，不扇出全员。只有流程签发的行动授权会唤醒对应智能体。一个房间最多一个活动流程。
- 群当前通过 SendToUser(text) 显式发言，必须带 `to:"room"` 或 `to:"dm"`，每回合最多 3 条；整轮不调用出口就是沉默。无论是否被点名，普通收尾文本都只是草稿，不进入群。面向全群的社交交流由每位成员各回复一条短消息并结束，禁止在回应中点名或引出工作。
- 独立回合只有携带有效 `replyRoute` 才能 `to:"room"`，提交的是候选行动，协议校验通过后才公开并自动接棒。
- 群只公开纯文本；to=dm 私发主人。交互卡走独立交互事件，文件交付走私聊/产物，不能把内部工具输出当成群消息。
- 同事 1:1 用 SendToAgent + 收件箱，发送即返回，回复属于后续回合；一封信一个回合，消费执行「领取 → 检查点 → 处理 → 确认」，失败有限退避，超限进 failed。群目标也只落盘入队，不等待成员执行，不返回开口/沉默人数。SendToAgent 不登记 registerChild；correlationId 不参与停止传播。
- 群调度对忙成员改为排队（E3.7）：投递进收件箱、等它空下来补一轮，不再跳过丢信；排队投递在离群/群解散后领取时撤销。
- 群扇出或同时联系多人遵循用户明确指示；同事传话保留必要的可执行信息。模型侧不提供删除同事、解散群的工具；工作台创建/改群要求用户回合授权，普通同事来信不能签发。工作台更新要求实际成员资格。

### 0.3 插话、停止和等待

- 普通用户新句抢占旧 Run：断流、标 parked，先处理新句，旧工作仍欠着；当前续跑依靠旧原文和内存树。
- 私聊停止词由运行时整句识别：去空白和末尾标点、拉丁小写匹配；词表可追加。不依赖模型自行判断或传播停止。
- 当前停止令遇到正在运行的用户回合会排队；回合结束依次处理停止、欠账续跑、同事来信。用户新句仍可抢占旧回合。
- 停止向已登记的子工作传播；同事停止不能打断对方正在服务用户的回合。开放群内停止仍是普通群文本，下一轮处理，不紧急中断。受控流程房间里用户说停止词：流程暂停、撤销活动授权，并以 `StopScope.room_flow` 取消相关票据。暂停后用户发「继续」「恢复」会恢复流程。
- 当前停止树与回执存在范围和关联问题，后文提出修复；不能因文字显示“停完了”就推断全部外部动作已终止。
- 用户发新句时作废未回答选项卡，不把这句自动当作选项答案。当前等待由内存 Broker 维护，默认 5 分钟；持久等待是 E4 目标。
- 输入框没有停止按钮，用户可发送停止词。增加新的入口或改变停止优先级必须作为明确的行为变更。

### 0.4 对话体验与运行边界

- 聊天区以用户可见正文、进展、交付物和交互卡为主；工具入参和结果收进过程抽屉。
- 私聊优先展示 SendToUser 交付的内容；若模型整轮没有调用出口，则用普通最终正文兜底，避免无回复。一旦调用过出口就压掉额外正文。群聊只展示明确出口和成员进行中状态，不使用正文兜底。
- 名字、活动、计数与用量取真实状态，不补假数据；通知优先用于需要用户行动的事情。
- 当前模型与执行工具按回合运行；Task 只实现 executor，工人不是侧边栏固定同事。工人管理和 TodoWrite 仍在内存。
- 当前 Shell 在本机执行，Read 读取本机文本；不能沿用旧文档“所有文件操作都被项目沙箱限制”的说法。附件交付具有自己的路径约束，具体见工具参考。
- 设置页可增删 OpenAI 兼容供应商与模型、保存 Key、切换思考等级，并热更新运行时 Provider；配置落在 `model-config.json`。时区、语言和每同事工具装卸仍未完成。
- 云电脑整组不做。本地关闭全部 Electron 窗口当前会停止后端并退出，托盘常驻是计划功能。

## 1. 产品目标与设计结论

用户创建一个同事，持续跟这个同事合作。今天私聊、明天群里讨论、后天回来追问，都是同一个身份。用户不用管理新会话，也不用反复交代来龙去脉。

工程上把四件事分开保存：

| 对象 | 回答的问题 | 生命周期 |
| --- | --- | --- |
| 同事 Agent | 谁在负责？有什么职责、能力和记忆？ | 长期存在 |
| 消息 Message | 谁在什么地方说了什么？ | 持续积累，可分页查看 |
| 工作 WorkItem | 答应了什么？做到哪里？还欠什么？ | 从接下工作到完成或取消 |
| 执行 Run | 这一次醒来具体做了什么？ | 一次有限的执行，可被打断 |

同一个同事可以负责多件工作，一件工作可以经历多次执行。一句闲聊可以没有工作对象。任务结束后，同事和双方关系继续存在。

用户界面始终以同事和群为入口。工作由系统自动关联，只有用户想看进度时才展开。固定身份不要求模型持续占用连接：收到消息、同事回信或到达约定时间时，再组装上下文并唤醒。

目标继续采用本地单用户、单个后端进程的模块化架构。复用 React、Electron、LLMProvider、AgentLoop、记忆分层和当前 SendToUser 群发言纪律。近期重点是可靠性和工作连续性。

| 收件箱消费改为领取-确认（E3.3）：领取带期限、失败有限退避、检查点先于模型调用落盘 | `src/agent/inbox.ts`、`src/server/runtime/inbox-processor.ts` | 强退后可按租约回收重做（已用真实子进程故障测试）；跨重启的启动扫描、单实例锁与 epoch 拒绝迟到写入属 E3.6 |
| 群忙碌成员改为排队（E3.7）：点名按完整成员快照解析，投递进收件箱、空下来补一轮 | `src/server/runtime/room-dispatcher.ts`、`src/server/runtime/inbox-processor.ts` | 忙的时候不再漏信；每轮配额的独立持久计数与「待看」界面归 E5 |
| 多封来信仍合并为一个回合，但逐封署名（E3.3） | `src/server/runtime/inbox-processor.ts` | 来源不再被压成一个无出处段落；每封信保留 messageId/correlationId |
| 新用户句抢占旧执行，续跑重新拿旧任务原文 | `src/server/runtime/run-executor.ts:resumeOwed` | 新要求与旧目标的关系缺少明确记录 |
| 停止下发包含 treeId，但消费时没有按该 ID 精确定位；回执按数量消费 | `src/server/runtime/stop-coordinator.ts:executeStop/awaitStopAcks` | 容易误停无关工作，无法准确说明谁已停 |
| 人机交互由内存 Promise 和计时器维持 | `src/interaction/broker.ts` | 等用户一天、重启后再答等场景没有持久交接点 |
| 最近消息转换未带上来源，压缩时用户角色统一写成“用户” | `src/llm/convert.ts`、`src/memory/compact.ts` | 旧的群话、同事来信可能失去作者及场景信息 |

因此需要补的是：工作记录、可靠投递、独立调度、可恢复的执行。现有身份与记忆模块保留，通过清晰接口逐步接入。

## 3. 用户应该感受到的行为

以“让测试同事跟进一次发测”为例：

1. 用户说“帮我跟进这次发测”，同事接下工作，记下交付标准。
2. 同事联系运维，记录正在等哪条回复，释放执行资源。
3. 用户补一句“先只测登录”，系统更新同一工作的范围；旧执行不能继续按旧范围派活。
4. 用户另问“今天星期几”，同事正常回答，发测工作仍然保留。
5. 用户关闭窗口，仍在运行的后端继续处理；彻底退出应用则停止运行，保存恢复依据。
6. 下次启动，收到的信、工作进度、等待事项仍在；已执行的动作先核对，再决定下一步。
7. 运维回信后，同事继续发测并把结果交给用户，无需用户新建会话。

侧边栏仍显示同事和群。同事顶栏显示“正在处理发测”“等运维回复”“等你确认”或“空闲”。右侧增加“手头的事”：目标、当前进度、下一步、在等谁、交付物、最近更新时间。

工作卡只是同事对自己工作的说明。用户可以点开、纠正、暂停或结束，也可以一直用自然语言沟通。

## 4. 数据模型

下列为领域字段草案，具体数据库迁移由实施阶段生成。所有实体使用稳定 ID；名字只作显示和输入解析。时间戳用于显示，顺序和并发判断使用单调序号及版本。

### 4.1 Agent：继续沿用固定身份

保留 `AgentRecord`。逐步补 `revision` 和工具配置版本，使每次执行可记录它使用的身份、工具和模型版本。修改名字、职责、模型不改变 agentId，也不拆分经历。

“长期身份”允许用户调整职责和同事积累经验。资料、用户指令与从聊天中抽取的事实分别存放，抽取记忆不能直接改写用户设定的职责。

### 4.2 WorkItem：持久保存承诺与进展

```ts
interface WorkItem {
  id: string;
  ownerAgentId: string;
  originMessageId: string;
  originChannel: { kind: 'dm' | 'room'; id: string };
  projectId?: string;
  title: string;
  objective: string;
  acceptance: string[];
  status: 'ready' | 'active' | 'waiting' | 'paused'
    | 'completed' | 'cancelled' | 'failed';
  progressSummary: string;
  nextAction?: string;
  revision: number;
  artifactIds: string[];
  createdAt: number;
  updatedAt: number;
  completedAt?: number;
}
```

配套 `WorkStep` 保存步骤、状态、结果引用；现有 TodoWrite 接入这些步骤。工作状态由服务层校验，不能只把模型最后一句话当成完成。

**实现位置（E4.1 已落地）**：类型与「任务 / 闲聊」判定在 `src/work/item.ts`，JSON 持久化在 `src/work/store.ts`（`work/items.json`，实现 `storage/ports.ts` 的 `WorkRepositoryPort`），状态机在 `src/work/service.ts`（唯一转换入口：受理建/续、追加步骤、条件更新、收尾校验）。HTTP 见 `GET /api/agents/:id/work`。受理私聊消息时旁路记录工作（不改发送/执行语义）；判定为闲聊则不建工作。

完成要求：有交付说明或结果引用、没有尚未解决的必要等待、必要步骤完成。服务层可验证文件存在、测试结果等客观条件；质量是否满足开放式目标仍允许用户复核并重新打开工作。

不为每句消息建工作：问候、简单问答只建 Run。需要多步执行、等待、派活、交付物或后续跟进时，建立 WorkItem；第一次有副作用的工作动作前完成关联。一次很快完成的工作也可以立即 completed。

### 4.3 WorkWait：等待是一条记录

字段：`id, workId, kind(user/agent/time/external), correlationId, dueAt?, status(pending/resolved/cancelled/expired), resultRef?`。

一件工作可以等多个结果。等待关系必须记录“等谁、哪次请求、满足什么条件”。进入 waiting 后结束当前 Run，释放同事执行权；匹配事件到达后创建新的 Run。

用户问题卡关联 WorkWait。保存问题、选项、状态和回答引用；密钥答案仅保存 SecretStore 引用。重启恢复待答卡，不试图序列化 Promise。超时只有业务确实需要时才设定，超时不能当作用户已经回答。

### 4.4 Run：一次执行与一件工作分开

字段：`id, agentId, workId?, triggerDeliveryId, status, checkpoint, leaseEpoch, workRevision?, startedAt, endedAt, stopReason, usage, error`。

状态：`queued → running → succeeded / yielded / cancelled / failed / interrupted`。

- succeeded：本次执行结束，工作可以仍是 waiting。
- yielded：被新消息抢占或主动让出，工作继续保留。
- interrupted：退出或崩溃留下的中断，需要恢复检查。
- checkpoint：已处理输入、已确认工具结果、进度摘要、下一步及上下文游标。保存可审计的事实，不保存隐藏推理。

AbortController、流连接和 Promise 属于内存中的执行句柄。持久化的是状态与恢复依据。

### 4.5 Message 与 Delivery：说过和处理过分别记账

Message 增加 `channelKind, channelId, authorKind, authorId, workId?, runId?, replyToMessageId?, seq`。消息是不可变内容；同事经历使用 `AgentObservation(agentId, messageId, observedAt)` 关联同一份正文，避免群正文在多处变成不同版本。

Delivery 字段：`id, messageId?, eventKind, payloadRef?, targetAgentId, workId?, correlationId?, priority, status, attempts, availableAt, leaseOwner?, leaseEpoch, leaseUntil?, lastError?, dedupeKey`。

状态：`pending → claimed → handled`，失败按策略回 pending 或进入 failed/cancelled。handled 表示输入已经形成持久决定或可继续的执行检查点，**不表示整件工作完成**。如果仅创建了 Run、还没处理输入，恢复必须接管该 Run，不能重新建一份工作。

所有消息保留原始发送者；批量交付时逐封列出作者、位置和关联工作，不再把多个人的文字压成一个无来源段落。

### 4.6 协作、工具调用与界面事件

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| Delegation | id、parentWorkId、childWorkId、fromAgentId、toAgentId、requestMessageId、replyCorrelationId、status | 精确知道派给谁哪件事；支持回复和停止 |
| ToolInvocation | id、runId、workId、operationKey、tool、argsRef、status、resultRef、replayPolicy | 避免恢复时盲目重做副作用 |
| UIEvent | seq、type、agentId、channelId、workId、payloadRef、createdAt | 断线重连补发已落盘的变化 |

后台 executor 是 WorkItem 的一次执行尝试，不进入同事注册表；其结果、取消关系和恢复状态要持久化。现有工具名 `Task` 可以兼容，内部使用 WorkItem/Run/WorkerAttempt，避免概念混用。

## 5. 新消息怎么接到正确的事情上

收信后先获得明确关联，再让模型处理内容：

1. 回复工作卡、用户答题、工具结果、同事回信：使用明确的 workId/correlationId。
2. 普通用户文本：在本次 Run 的前置阶段，结合最近交流与未完工作的短列表判断。
3. 输出结构化关系：`continue(workId)`、`revise(workId)`、`new_work`、`chat`；停止命令另走运行时。
4. 服务层校验 workId 的归属、状态和 revision，再写入关联。
5. 多个对象都可能指代且会导致实际动作做错时，在对话里短问一句；先完成不依赖该答案的内容。

“先只测登录”是修订；“顺便解释这个报错”可能是另一件事；“继续昨天那个”从未完工作及近期记录检索。避免把任何新句都自动建成新工作，也避免把所有新句强塞进上一件事。

修订时递增 work.revision，保存变化与来源。旧 Run 的工具执行和状态提交必须检查版本；有冲突则让出，按最新目标重新组装。旧结果可作为历史事实保存，不能把新工作覆盖成旧状态。

## 6. 持久调度与可靠投递

### 6.1 模块边界

| 模块 | 负责 | 复用/改造位置 |
| --- | --- | --- |
| ConversationService | 接收消息、工作关联、产生投递 | 抽离 HTTP 中的执行入口 |
| WorkService | 工作状态、步骤、等待、派活与取消范围 | 新增 `src/work/` |
| Scheduler | 领取事件、同事执行权、优先级、重试、唤醒 | 新增 `src/runtime/scheduler.ts` |
| RunExecutor | 组装上下文、运行 AgentLoop、提交结果 | 拆分 `src/server/runtime.ts` |
| DeliveryService | 私聊、群聊、同事信的统一可靠投递 | 替换清空式 inbox |
| RecoveryService | 启动恢复、租约过期、未知工具结果核对 | 新增 `src/runtime/recovery.ts` |
| EventStream | 持久事件订阅与重放 | 独立于发送请求的 SSE |

这些是同一后端进程中的模块。避免引入微服务、消息中间件或复杂分布式编排。

### 6.2 接收和消费事务

接收时，在同一事务内写入消息、对应观察记录/收件人快照、Delivery 和 UIEvent；提交成功后才返回“已收到”。客户端提供唯一 clientMessageId，重发返回原来的收据。

调度器原子领取 Delivery，并为 agent 取得递增的 leaseEpoch。同一个 agent 同时只有一个有效的前台模型执行；耗时工作可以交给受跟踪的 executor。模型调用和网络 I/O 不占用数据库事务。

每个工具结果、工作变更、待发协作消息及 UIEvent 在短事务内提交。内部传话的目标 Delivery 与派活关系同事务写入，不存在“发送成功但派活关系没记下”的中间状态。

领取不删除消息。异常后从已记录的检查点续接；超过有限重试次数进入 failed，给用户一个可重试的状态。永久参数错误不反复重试；临时错误采用退避。恢复和重试共用持久计数，不能重启就重置预算。

执行控制的 `autoActivation` 每个智能体一条，落在控制存储里。新建同事务必登记 `enabled`（`AgentRuntime.createAgent` / `enrollAgent`，工作台建同事走同一回调）；启动时 `migrateExistingAgents` 只给「控制存储建立前就存在」的旧智能体补 `paused` 待确认，不会把新建的同事判成暂停。

### 6.3 插话与串行性

用户新句先持久接收并回执，再请求旧 Run 让出。推进步骤：撤销旧执行的有效 epoch → abort 旧调用 → 新 Run 处理新话。写入工作、发布回复或执行新副作用前均检查 epoch；过期执行的流式内容不再发布。

已经在外部发生的动作无法通过撤销 epoch 回滚。旧调用晚到的结果写入原 ToolInvocation 供核对，不直接修改新目标；新执行必须看到这些待核对状态。

相关工作被修订就按新版本续做；无关闲聊结束后重新调度 ready 的工作。恢复前检查 waiting、paused、cancelled 和新目标，不再无条件重放旧用户原文。

用户消息优先；同事来信、群广播、例程排队并有等待时长提升，避免长期饥饿。调度并发、单次步数、累计重试、自动续跑和例程费用设可配置上限；达到上限明确进入等待或失败，不能假装完成。

### 6.4 群聊

按发送时的完整成员名单解析 @，并保存收件人快照。忙碌成员仍获得 Delivery，处理显示为“待看”；离群后撤销尚未处理的投递，新成员不获得入群前消息。

保留现有点名、补充、二次叫醒的发言规则及每轮上限。面向全群的社交交流要求全员各回应一次，但不得产生新的点名链或任务。群流程记录每位成员 pending/spoke/silent/failed。晚到处理先读取允许看到的后续群消息，检查问题是否已解决；可以沉默，但不得默默丢信。

同一 rootRoundId 的召唤次数和发言配额持久化，重投、重启不能重置。所有成员都通过是否调用 SendToUser(text) 决定发言；被点名者由群回合提示明确要求调用出口回应，不再用普通收尾文本兜底。

## 7. 停止、等待与恢复

### 7.1 停止必须有精确范围

停止生成 `CancelRequest(id, targetWorkIds, cutoffSeq, requestedBy, status)`。有明确关联时停指定工作及其委派后代；裸“停”默认作用于该同事在该命令前已接下的未完工作，与当前“停旧树”的范围接近。停止后新收到的工作不受影响。

每条委派关联真正的 childWorkId；停止下发使用 cancelId + childWorkId，接收者只取消对应工作。回执使用唯一 `(cancelId, childWorkId)` 去重，不能只按收到几封信计数。部分超时显示“本地已停止，仍有 N 项未确认”，后续回执更新状态。

保留当前“同事发来的停止令不打断正在服务用户的回合”“群内停止通过普通群消息在下一轮处理”的行为。建议调整**用户亲自发给本同事**的停止：收到后立即阻止目标工作派发新动作，并请求中止；这是相对当前 stopOrQueue 的行为调整，实施时单独更新本文当前行为约定和回归用例。

前台逻辑 Run 被取消不代表外部进程已经终止。区分请求停止、已确认停止和状态未知；取消不能抹去已产生的文件或已发出的消息。

### 7.2 等待用户

持久 WorkWait 替代长期悬挂的 Promise。保留当前“用户新句作废未回答选项卡、不把新句当成选项答案”的规则：作废该卡并写入状态，再分析新句；工作本身继续存在，是否还需要等待由新一轮判断。

刷新或断开连接不作废卡片。带交互 ID 的明确答案才能完成对应等待。过期卡、已作废卡的迟到回答返回明确状态，不误解成其他工作的答案。

### 7.3 恢复工具副作用

**当前状态（E3.5）**：账本与分类已落地——`src/storage/tool-ledger.ts`（执行前记意图、执行后回填结果，未完结的留在 `unfinished()`）、`src/tools/policy.ts`（稳定 operationKey 与 rerun/verify/manual 分类）；启动扫描与自动恢复尚未开启（E3.6）。

ToolInvocation 在调用外部工具前记录 started，返回后记录结果。外部动作和本地事务无法合成一次原子操作，因此恢复语义采用“至少一次投递 + 幂等提交 + 未知结果核对”。

| 调用类型 | 中断后的恢复策略 |
| --- | --- |
| 纯读取、搜索 | 可以重新读取，注明时间变化 |
| 支持业务幂等键的接口 | 用稳定 operationKey 重试；不能为每次 Run 生成新业务键 |
| 文件生成/覆盖 | 使用暂存文件、原子替换与预期内容摘要，核对后决定是否重做 |
| 任意 shell、无幂等支持的外部发送 | started 但无结果时标 unknown，先查产物/外部状态；无法判断则等待用户决定 |

不承诺所有工具 exactly-once。数据库去重只能约束本地提交。若旧执行的外部动作仍可能运行，对冲突资源暂停新副作用，先完成核对。

### 7.4 启动和退出

**当前状态（E3.6）**：已落地「取单实例锁 → 启动扫描」——`storage/instance-lock.ts`（另一个活进程持有就拒绝启动，崩溃留下的锁能接管）、`AgentRuntime.recover()`（上次进程没回填结果的工具调用标 unknown 并给核对计划；未确认来信一律重投并接着办）。数据库迁移与 running Run 的 interrupted 标记随持久账本落地。

启动顺序：取得数据目录单实例锁 → 打开数据库及迁移 → 将旧进程的 running Run 标 interrupted → 处理 unknown 调用 → 恢复等待、到期事件和待投递消息 → 启动调度与 UI 订阅。

暂停、取消和终态工作不会因重启复活。只重新评估 ready、可恢复 interrupted 和已经满足条件的 waiting。

第一阶段保持现有本地生命周期：彻底退出应用后不运行；再次启动可恢复。执行计划 E6 再支持关闭窗口留在托盘、显式退出终止后端。完全退出或电脑休眠时不承诺执行；将来若要全天在线，需要另行选择常驻服务或远端部署。

后台进程必须由执行器记录可核对的进程身份和作业 ID；不能在重启后只凭旧 PID 杀进程。检查点和可读的进度摘要是恢复的主要依据。

## 8. 记忆与上下文：同一个人处理不同的事情

保留三层 × 三作用域记忆，在每轮加入工作事实。上下文装配顺序：

1. 固定身份、用户指令、本轮发言位置与工具规则。
2. 当前工作目标、版本、验收标准、最近检查点、待确认副作用。
3. 本次触发事件：作者、频道、明确关联、原文。
4. 当前工作相关的近期原文、历史片段和摘要。
5. 同事自己的长期记忆、共用用户信息和有权访问的项目记忆。
6. 其他未完成工作的短列表，供关联新消息和安排后续使用。

项目加入资格不自动授权读取其他同事的私聊；共享的是项目笔记及明确共享的交付物。同事经历可以跨私聊和群聊检索，面向群的输出仍遵守用户对私下信息的约定。

记忆描述“知道什么”，工作记录描述“还要做什么”。工作完成/取消以 WorkService 为准；过时日志不能覆盖当前工作状态。摘要保留 messageId/seq 覆盖范围、作者、频道、workId 和来源引用。

现有压缩器先截 48,000 字符，却把 coversUpTo 推到整批末尾。改成按消息边界分块，只推进实际纳入摘要的序号。工具调用及结果成组保存；中断造成的未决调用先核对，再生成合法的模型输入。

预算统一计算身份、工具 schema、工作、记忆、原文、输出预留。现在 builder 在分配后另设多处最低预算，实施时需统一到一个分配器。当前输入过长应分块/附件化或明确反馈，不能静默裁掉改变任务意思的部分。

记忆抽取与摘要更新作为可重试维护工作，按来源 ID 幂等处理。失败只影响记忆更新，不抹去已经提交的工作结果。初期继续词法检索，先用真实连续对话样例验证遗漏，再决定是否引入语义检索。

## 9. 存储与 API

### 9.1 SQLite 保存需要共同提交的状态

建议新增 `.agentbot/state.sqlite`，统一保存身份/成员元数据、消息、观察记录、工作、步骤、等待、执行、投递、委派、工具调用和 UI 事件。文件产物仍存在工作目录；记忆和摘要初期可保留原文件格式，作为可重建的派生数据，通过幂等维护事件更新。

选择 SQLite 的理由是这些记录需要事务边界：例如“收信成功”和“待处理任务存在”必须一起成立。SQLite 提供事务原子性，适合这里的本地事务存储。[官方说明](https://www.sqlite.org/transactional.html)

用 Repository 接口封装 SQL；短事务内禁止模型和网络请求。启用外键，设置 busy timeout，明确 WAL/同步策略，并验证实际备份与断电恢复要求。只允许一个 AgentBot 后端持有数据目录执行锁；数据库连接可有多个，但不运行两套调度器。

**运行时兼容门槛**：当前 package.json 声明 Node ≥20.3；node:sqlite 从 v22.5.0 才加入，不能照旧文档宣称 Node 20.3 自带该模块。本机命令行检测为 Node v24.8.0、模块可用且有实验性提示；Electron 的实际运行时尚未核验。[Node 官方文档](https://nodejs.org/api/sqlite.html)

执行计划 E1 固定并验证 CLI 与 Electron 的运行时版本和所需 SQLite API，再决定使用内置驱动。若目标运行时不支持，则选可打包的驱动并验证 Electron 兼容；不能只在开发机测通就切换存储。

关键约束：clientMessageId 唯一；Delivery.dedupeKey 唯一；同一 agent 只有一个有效执行权；同一事件的逻辑 Run 创建去重；operationKey 在业务工作内唯一；回执按 cancelId/childWorkId 去重；WorkItem.revision 条件更新。

### 9.2 发送和订阅分离

| API 提案 | 行为 |
| --- | --- |
| `POST /api/agents/:id/messages` | 接收 clientMessageId、正文、可选回复引用；提交后 202 返回 messageId、receiptSeq 和已知 workId |
| `POST /api/rooms/:id/messages` | 同样先落盘回执，按成员快照投递 |
| `GET /api/events?after=seq` | SSE 持续推送状态变化，支持断线补发 |
| `GET /api/agents/:id/work` | 获取手头工作、等待、进展 |
| `GET /api/work/:id` | 工作详情、步骤、产物与可见活动 |
| `POST /api/work/:id/actions` | 暂停、继续、取消、重新打开；带 expectedRevision 和 requestId |
| `POST /api/interactions/:id/answer` | 幂等提交明确答案，唤醒对应等待 |

前端用 messageId/runId 归并消息，用 seq 去重；断开 SSE 只释放订阅资源。token delta 可以是短暂事件，最终文本和工作状态必须持久化。重连先取快照，再从快照游标补事件，避免取快照期间漏更新；旧游标超出保留期时服务端要求重新取快照。

旧 `/api/chat`、bots/sessions 入口暂时做兼容适配，调用同一收信服务。发送请求的取消不撤销已经提交的消息；明确停止走停止语义。
