# 消息身份与智能体往来

## 问题与边界

模型的 `role: user` 只代表模型输入，不代表人类用户。过去同事来信、群成员经历都以 user 存储，前后端又把 user 直接映射为右侧气泡；历史转模型时也丢了作者信息。此外，工作台代群发言曾将真实发送者写死为 owner。

现在使用三类独立信息：

- `role`：模型协议角色，仍保持合法的 user/assistant/tool 序列。
- `sender`：真实发送者的 kind/id/name/color/avatar 快照，名字变化不影响稳定身份。
- `source`、roomId/roomName：触发来源及群归属，不用于冒充发送者。

共享的 `messageIdentity` 同时服务历史 Presenter 和实时 reducer。只有真实私聊用户输入才匹配本地待发占位；同样的文本不意味着同一条消息。同事与群消息转换给模型、摘要和记忆抽取时也保留来源标签。

## 往来档案与队列

`SendToAgent` 私信的 `InboxItem.id` 同时是原始投递 ID。受理时保存双方身份；`CorrespondenceStore` 按该 ID 幂等归档至 `correspondence/accepted.jsonl`。档案只含双方真实发送的原文，不读取彼此其他私聊，不把工具结果或模型自述当成已发送的回复。

- Inbox 是执行队列；档案是只读往来记录，不负责唤醒或重放任务。
- enqueue 成功后归档；消费确认前再次保证归档；启动恢复补齐尚在队列里的普通来信。因此队列确认删除后档案仍保留。
- 这不是跨文件事务。入队后归档失败时，该消息仍可能已受理；不能据工具错误盲目重发。沿用可能有副作用的失败任务不自动重放策略。
- 一封来信一个独立回合，不合并不同发送者。task 的 correspondenceIds 让 UI 隐藏重复的模型输入正文；兼容旧合批记录的显示。
- 实时档案事件发到双方频道，快照也从同一档案投影，客户端按投递 ID 去重。
- 当前本机 JSONL 档案仍是全量加载；详情 HTTP 每页默认 30、最多 50 条，主聊天快照沿用现有历史加载方式。大规模归档索引/历史分页属于后续存储工作，不声称已解决无限历史内存增长。

## 界面

主聊天中的相邻往来折叠为“已发消息给 / 消息来自 / N 条消息往来”，带对方头像与名称。选择参与者打开双方只读原文，顶部显示 A ↔ B，每条注明发送方向和时间；底部明确仅供查看，没有输入框。

`GET /api/agents/:id/correspondence/:peerId?before=<投递ID>&limit=30` 只返回这对智能体的往来，不提供 POST 发送接口。不改变现有本机 HTTP 服务的访问控制边界。

群消息继续走群时间线；每个智能体的经历里保留群名和作者，实时与刷新一致。工作台代发显式传调用者 ID，不能依赖“排除哪个成员”推断作者。

## 旧数据

没有 sender 的旧记录按已有 source/speaker 展示；来源不明时明确标记“来源未记录”，不分析正文来猜作者。已经被旧代码错误写成 owner 的群消息、已经消费删除且未归档的老投递，无法可靠自动还原完整往来链路。此次不重写真实聊天历史；新往来记录从升级后开始完整保存。
