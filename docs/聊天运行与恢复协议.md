# 聊天运行与恢复协议

本轮实现于 2026-09-13。范围是聊天控制面，不更换模型、SSE、React、Node 或现有群调度器。
2026-09-13 修订：用户停止立即生效，不再排队等待正在执行的用户任务；停止确认后旧来信不能自动复活当前智能体。准入与停止以 `RuntimeControlStore` 为事实源。
参考 `IdeaProjects/agent` 的运行与连接解耦、明确游标、客户端状态引擎；不照搬其单会话单活跃运行约束。

## 1. 所有权与调用方向

```text
HTTP / CLI / 内部发送
  → 命令受理（按频道 + clientMessageId 串行去重）
  → ChatRunCoordinator（运行记录、事件绑定、唯一收尾）
      → RunExecutor（抢占、任务树、模型、工具、记忆）
      → RoomDispatcher（群父运行 → 成员子运行 / 延迟投递）
      → StopCoordinator（停止命令）
  → EventJournal（epoch + seq、限量重放）
  → SSE（仅观察）

消息事实 + 运行记录 → chatSnapshot → 客户端恢复
SSE → EventClient → ChatEngine → React 适配器 → 页面
```

- `ChatRunCoordinator` 不依赖 HTTP/SSE 连接，不负责调用模型和工具。
- `RunExecutor.runTurn` 是所有成员执行（含自动续跑、收件箱）的统一运行入口。原来的上层 `runJournaled` / 各入口自行发 done 已移除。
- 群扇出、延迟投递有自己的父运行；成员执行有子运行。事件绑定保留原始外部观察者，嵌套/复制 options 不重复发布父日志。
- `ChatEngine` 独占聊天消息与运行状态；`useWorkspace` 不再覆盖聊天历史。页面切换、完成后刷新、重连恢复均通过引擎加载快照。

## 2. 身份与状态

| 字段 | 含义 |
| --- | --- |
| channelId | UI 频道（私聊 agentId，群聊 roomId），不作为执行身份 |
| clientMessageId | 一次用户提交的幂等键，作用域为频道；未知受理结果的重试复用它 |
| runId | 一次执行。也用于新执行的 RunLedger / 工具账本 / TaskProgress 检查点 |
| taskId | 任务链标识。续跑另建 runId，继承 taskId |
| parentRunId | 续跑所接续的运行，或群成员/延迟投递的父运行 |
| messageId / callId | 消息与工具调用身份；按 ID 去重、回填，不按正文猜测 |
| epoch + seq | 事件流代际和代内连续序号，不能拿 runId / 时间戳代替 |

```text
queued → running → finalizing → succeeded
                  ↘ incomplete / parked / cancelled / failed
进程重建：上次仍活跃的运行 → interrupted
```

`parked` 结束的是本次执行，不是整个任务。后续接续是新运行；不能把旧运行改回 running。
群父运行结束表示这次扇出已结束，不保证每个成员任务成功；排队成员稍后建立关联的新运行。
`finalizing` 表示答案已交付、仍有记忆等收尾：busy 可为真，但不能再出现“正在处理”占位。
已终止运行不回到活跃状态。重复 done 和迟到的 queued 回执不能复活运行。
运行失败/中断后尚未收到结果的工具卡退出 running，提示结果未确认，不假称工具成功。

## 3. 受理、幂等与持久化

- 命令按 `频道 + clientMessageId` 串行受理；不同频道互不阻塞。
- 持久运行记录先于执行。同键不同正文/模型等参数报错，同键相同请求返回原 runId。
- 私聊用户消息先落库再发 202。群 202 表示运行意图已持久化，群时间线消息仍在执行开始时写入。
- 同一运行在内存中只拥有一个执行 Promise。重复调用不会重复进入模型。
- 未确认受理（断网/回执丢失）的重试复用原幂等键；已明确失败后的再次尝试创建新命令。
- `chat/runs.json` 保存运行控制面，`writeJsonAtomic` 异步原子替换（同文件串行）、0600 权限；**写入完成才对外发布运行事件**，受理要等落盘完成再返回。最近 1000 条终态记录之外的记录会被裁剪，活动/挂起运行保留。已结束运行（成功/取消/未完成/失败/中断）的输入只留前 500 字并记原始长度 `inputLength`，幂等比对仍用保留的 `commandHash`；运行中/挂起的保留完整输入。界面「重试」要发的原话从对话里那条用户消息取（`chat-engine` 按 `run.messageId` 找，找不到才回落到账本摘要），账本不承担原文存储。去重走 `channelId + clientMessageId` 索引，幂等保证限于记录保留窗口。
- 兼容读取旧私聊 `received/index.json`。旧消息不需要批量迁移，新增消息开始携带 runId。
- 现有单实例数据目录锁仍是前提。JSON 文件之间不是数据库事务；强退后的不确定执行明确标 interrupted，不承诺跨文件 exactly-once。
- 现有 RunLedger 恢复策略仍可发起新的任务续跑，保留已有“未知工具先核对”约束；不会重新执行旧 runId。

## 4. 恢复协议

`GET /api/chat/state?channels=id1,id2` 返回 `{ cursor: {epoch, seq}, channels, runs }`。
同时携带当前待回答的 interactions；刷新/重连不丢确认卡，较旧快照不能复活已关闭的卡。

1. 从持久消息生成展示视图，并读取运行记录。
2. 若读取期间事件序号发生变化，重读（最多 5 次）；失败返回错误，客户端不得推进游标。
3. 客户端应用快照之后，再订阅 `/api/events?after=seq&epoch=epoch`。
4. `ready.latestSeq` 只是服务端信息，绝不是客户端已消费水位。
5. 事件按连续 seq 消费，成功应用后才推进；重复事件丢弃。
6. 缺口、保留窗口过期或 epoch 不同，关闭旧流，重新恢复快照，再订阅。

消息落盘与事件发布之间可能存在一个极短窗口：快照可以提前包含即将发布的消息。它们是同 ID 的持久事实，重放按 ID 合并，不重复追加。
历史晚到时按水位合并，不能覆盖更新的消息/工具结果。新权威快照可替换已确认历史，保留本地待受理消息和错误。
不同快照加载在引擎内串行，避免旧服务响应覆盖新 epoch 状态。
运行控制面每 10 秒对账（仅存在忙碌/待受理状态时），兜住最后一条终态丢失。

## 5. 容量与失败隔离

- EventJournal 保留最多 2000 条、8 MiB；过期就恢复，不无限积累。
- 客户端单个 SSE 缓冲上限 4 MiB；解析/协议失败会取消并释放旧 reader。
- 订阅者/外部 UI 回调失败不反向让已执行的模型或工具失败。
- 快照读取失败保持已有界面并重试，不吞错后跳游标。
- 空的无工具私聊回复明确判失败；群聊保持允许沉默。

## 6. 验收与未扩展范围

`test/chat-architecture.test.ts` 直接测试无框架 EventClient / ChatEngine，并用 FakeProvider 驱动真实 Runtime：
游标补发、epoch 切换、缺口、快照失败、旧流释放、终态先到、旧历史晚到、双端用户消息、重试原键、工具卡收尾、并发受理/执行、自动续跑、群父子运行和启动中断。
群延迟投递在 `test/room-queue.test.ts` 额外验证“既落库也发布，且只发布一次”。

不在本轮扩展：多实例部署、Redis、跨存储分布式事务、聊天历史分页、用量统计、全新群调度算法。
事件日志仍是有界内存窗口；跨重启恢复依赖持久消息和运行状态，不声称保存每个 token 的永久事件日志。
