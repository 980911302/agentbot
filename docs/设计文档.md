## 1. 目标与边界

### 1.1 要解决的问题

做一个**本地运行的、多智能体协作的 AI 工作台**，满足三条：

1. **每个智能体有自己的长期记忆**（不是全产品一份用户档案）
2. **群聊是广播，不是中心 AI**（成员各自决定说还是不说）
3. **上下文没有硬上限的体感**（旧对话压成摘要，旧记忆靠检索）

### 1.2 明确的边界

| 不做 | 原因 |
| --- | --- |
| 群作为记忆库 | 群只是成员表 + 共享时间线，思考发生在成员各自的回合里 |
| 中心仲裁者决定谁发言 | 每个成员独立走判断树，`@` 是强信号不是调度指令 |
| 向量检索 / embedding | 当前用词法打分（中文 bigram + 拉丁词），零外部依赖 |
| 多用户 / 权限系统 | 单用户本地应用，`owner` 概念只用于区分记忆作用域 |
| 云端持久化 | 一切落在项目根 `.agentbot/`，可用 git 管理 |

### 1.3 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Node.js ≥ 20.3 + ESM | 原生 `fetch`、`AbortSignal.any`、`node:sqlite` 可用 |
| 语言 | TypeScript 7（strict + `noUncheckedIndexedAccess`） | 全链路类型即文档 |
| 后端依赖 | **零运行时依赖** | 手写 HTTP/SSE、手写存储，避免供应链与升级负担 |
| 前端 | React 19 + Vite 8 | 流式事件驱动 UI |
| 桌面端 | Electron 44 | 内置后端进程，双击即用 |
| 模型 | DeepSeek（OpenAI 兼容接口） | 走标准 `/chat/completions`，任何兼容端点都能替换 |
| 密钥 | **只从环境变量或 `.env` 读** | 源码不含默认密钥；缺 key 时启动即失败并给出指引 |

## 3. 数据模型

### 3.1 Agent

```ts
interface AgentRecord {          // 持久化形态（agents.json）
  id: string;
  name: string;
  instructions: string;          // 角色与职责
  toolNames: string[];           // 装载哪些工具
  color: string;                 // 头像底色
  projectIds: string[];          // 参与的项目，决定能读哪些项目笔记
  createdAt: number;
  updatedAt: number;
}

interface Agent extends AgentRecord {   // 运行时形态
  tools: Tool<any>[];            // 由 toolNames 解析出来的实例
  memory: AgentMemory;           // 此刻可见的记忆引用
}
```

**设计要点**:`AgentRecord` 是磁盘上的事实，`Agent` 是某一刻组装出来的工作副本。每次回合开始都重新组装，保证记忆是最新的。

### 3.2 Message

```ts
interface Message {
  id: string;
  agentId: string;               // 属于哪个智能体
  role: 'user' | 'assistant' | 'tool';
  content: MessageContent;       // 三种形态之一
  createdAt: number;
  roomId?: string;               // 群回合才有
  roomName?: string;
  speaker?: string;              // 这一轮谁在说话
  source?: 'user' | 'room' | 'agent';
}

type MessageContent =
  | { type: 'text'; text: string }
  | { type: 'tool_calls'; calls: ToolCall[] }
  | { type: 'tool_result'; callId: string; name: string; result: string; durationMs: number; ok: boolean };
```

**设计要点**:

- 一次工具调用落成**两条**消息（`tool_calls` + `tool_result`），用 `callId` 关联
- **私聊和群聊是同一条消息流**，靠 `roomId` 标记来源，不分两套存储
- `speaker` 让智能体知道「这句话是谁说的」（主人 / 某个同事）

### 3.3 Memory

```ts
type MemoryScope = 'self' | 'user' | 'project';   // 记在谁的本子上
type MemoryTier  = 'portrait' | 'log' | 'scratch'; // 三层

interface MemoryEntry {
  id: string;
  scope: MemoryScope;
  tier: MemoryTier;
  ownerId: string;               // self→agentId；user→'user'；project→projectId
  text: string;
  key: string;                   // 归一化指纹，用于去重
  tags: string[];
  source: 'user' | 'agent' | 'extracted';
  createdAt: number;
  updatedAt: number;
  lastSurfacedAt: number | null; // 最近一次进上下文
  hits: number;
}
```

**作用域 × 层级的可见性矩阵**:

| 作用域 | 谁能读 | 典型内容 |
| --- | --- | --- |
| `self` | 只有这个智能体 | 它跟你合作的细节、它在群里听到并决定记下的话 |
| `user` | **所有**智能体 | 名字、时区、跨助手都成立的偏好 |
| `project` | 参与该项目的智能体 | 端口、约定、部署规则 |

群没有作用域——群话若被记住，是某个成员写进**自己的**笔记。

### 3.4 Room

```ts
interface Room {
  id: string;
  name: string;
  memberIds: string[];           // 上限 6，至少 1
  createdAt: number;
  updatedAt: number;
}

interface RoomMessage {
  id: string;
  roomId: string;
  roundId: string;               // 同一轮扇出共享
  senderKind: 'user' | 'agent' | 'system';
  senderId: string;
  senderName: string;
  text: string;
  mentions: string[];            // 解析出的被点名成员 id
  everyone: boolean;
  createdAt: number;
}
```

### 3.5 存储布局

```
.agentbot/
├── agents.json                     智能体注册表
├── rooms/
│   ├── index.json                  房间表
│   └── <roomId>.jsonl              共享时间线（追加式）
├── messages/
│   └── <agentId>.jsonl             该智能体的全部消息（追加式）
├── memory/
│   ├── user.json                   共用的「关于你」
│   ├── agents/<agentId>.json       它的笔记
│   └── projects/<projectId>.json   项目笔记
├── compaction/
│   └── <agentId>.json              压缩摘要状态
└── inbox/
    └── <agentId>.json              智能体 1:1 收件箱
```

**为什么混用 JSON 和 JSONL**:

- 消息和时间线是**只追加**的，用 JSONL —— 写一条不需要重写整个文件，进程崩溃最多丢最后一行
- 注册表、记忆、房间表需要**就地修改**（改层级、拉人踢人），用 JSON —— 结构清晰、便于人工查看

**缓存策略**:`MessageStore` / `MemoryStore` / `RoomStore` 都在内存里持有文档副本，写操作同步更新内存与磁盘。冷启动时从文件重建。

## 4. 关键设计决策

### 决策一:Context ≠ Message History

**问题**:如果每次把全部历史丢给模型，token 会线性膨胀直到撞上限。

**方案**:`ContextBuilder.build()` 每次重新组装「这一轮真正送进模型的东西」，产物是**七段结构**，而不是历史消息的切片。

```
┌──────────────────────────────┐
│ System                       │
│  ├─ Agent 角色 / 职责         │  ← instructions（固定）
│  ├─ 本轮规则简报              │  ← 群回合的发言纪律
│  ├─ 画像（自己的 + 项目）      │  ← 每层配额内的
│  ├─ 关于你（共用）            │  ← 所有智能体都带
│  ├─ 日志近况                  │  ← 只带最近一小段
│  ├─ 随手笔记                  │  ← 只带新鲜的一小撮
│  ├─ 相关检索                  │  ← 眼前没有但和任务相关的
│  ├─ 更早的对话摘要            │  ← 压缩产物
│  └─ 工作文件                  │  ← 从 tool_calls 提取的路径
├──────────────────────────────┤
│ 最近原文（原子组，成对保留）   │
├──────────────────────────────┤
│ 当前任务                      │
└──────────────────────────────┘
```

**关键差别**:历史消息只占其中一段（最近原文），其余都是从记忆和摘要里**重新渲染**的。

### 决策二:按「原子组」裁剪，而不是按消息

**问题（真实踩过的坑）**:前 400 报错的根因——按 token 从后往前切消息，会把 assistant 的 `tool_calls` 切掉、只留下它的 `tool` 结果，DeepSeek 直接拒绝：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

**方案**:`groupMessages()` 把消息切成原子组，`tool_calls` 与它的结果**同进同出**；找不到父亲的孤立 tool 结果直接丢弃。

```ts
// 一条 tool_calls + 它引发的全部 tool_result = 一个组
// 裁剪时以组为单位，要么整组留下，要么整组丢弃
```

### 决策三:三层记忆 + 溢出降级而非报错

**问题**:「记忆满了怎么办」是这类产品的体验杀手。

**方案**:三层各有不同的老化策略，**没有硬顶**。

| 层 | 进眼前配额 | 保留上限 | 超容量动作 | 生存时间 |
| --- | --- | --- | --- | --- |
| 画像 `portrait` | 12 条 | 40 条 | **降级为日志** | 永久 |
| 日志 `log` | 8 条 | 600 条 | 淘汰最旧的 | 永久（可搜） |
| 随手 `scratch` | 6 条 | 80 条 | 淘汰最旧的 | 24 小时 |

关键在**降级**：画像装不下时变成日志，而不是被丢掉。用户体感是「细节变稀」而不是「突然失忆」。

### 决策四:去重先看数字

**问题**:「端口是 8080」和「端口是 9090」词面高度相似，天真实现会把它们合并成一条——这是数据损坏。

**方案**:三级判定，**数字守卫优先**。

```
1. 数字守卫    两条事实的数字集合不同 → 直接判为两件事，不合并
2. 完全相同    归一化指纹一致（去标点、全角转半角、小写）
3. 词面重合    Jaccard ≥ 0.86
4. 实词重合    去掉虚词后较小一侧覆盖率 ≥ 0.75（处理「我叫张林」≈「用户叫张林」）
```

**实测**:10 条用例全通过，包括「同义改写应合并」与「端口不同不应合并」两类对抗样本。

### 决策五:群是扇出，不是中心 AI

**问题**:直觉做法是「群里有个主持人 AI 决定谁说话」。

**方案**:没有主持人。入站消息由投递器**扇出给全体成员**，每个成员独立走判断树：

```
被叫醒
  │
  ├─ 我被 @ 了 或 @everyone？ ── 是 ──→ 必须开口
  │                                      （连 stay_silent 工具都不提供）
  └─ 否
      │
      └─ 有别人还没说过的、且归我管的实质内容？
            ├─ 有 → 用 say 工具开口
            └─ 没有 → 闭嘴结束回合（一等公民的结果，不是失败）
```

**为什么 `@` 不是投递开关**:文档明确要求「在场成员都会进入这一轮，再由各自决定说不说」。只投递给被 @ 的人会丢失「别人补充信息」的行为。

**为什么沉默要做成工具**:`stay_silent` 是一个显式动作。让模型「选择不说话」比让它「什么都不做」更可靠——后者经常表现为输出一段废话。

### 决策六:被点名者的收尾文本算发言

**问题（实测发现）**:即使移除了 `stay_silent`，模型仍可能不调 `say`，而是直接在 `content` 里输出一段话。按「只有 `say` 才算开口」的严格规则，被点名的人会离奇沉默。

**方案**:按是否被点名分开处理：

| 情况 | 收尾文本怎么算 |
| --- | --- |
| **被点名** | 直接算作发言（模型想说但没走工具，不惩罚它） |
| **未被点名** | 不算发言，只有显式调用 `say` 才进房间（防止刷屏） |

### 决策七:1:1 传话是队列，不是 RPC

**问题**:如果 `send_to_agent` 同步等对方回复，两个智能体互发就会死锁。

**方案**:投递即返回，对方的回复是**之后的一个新回合**。

```
A 的回合 ──send_to_agent──→ 写入 B 的收件箱 ──→ A 的回合继续/结束
                                    │
                          B 空闲时 drainInbox()
                                    │
                          积压消息合并成一个回合处理
```

**防无限互发**:传话链带 `depth`，上限 3（`DEFAULT_MAX_AGENT_DEPTH`），到顶后智能体被告知「直接把结论说给用户」。

### 决策八:token 估算用字符类别加权

**问题**:中文和拉丁文的 token/字符比差异巨大（约 0.9 vs 0.28），用统一系数会让预算失控。

**方案**:

```ts
estimateTokens(text) = ceil( CJK字符数 × 0.9 + 其他字符数 ÷ 3.6 )
```

零依赖、可预测、对中英混排足够准。真实计费以 provider 返回的 `usage` 为准（已采集但暂未用于配额）。

### 决策九:召唤队列 + 三波扇出

**问题（两件事撞在一起）**

1. 规格要求「群里 `@名字` 把话题甩给同事」——但最初只解析用户入站那一次，
   成员 A 发言里 `@测试运维` 不会把人叫起来。
2. 扇出是串行的：4 个成员 ≈ 4 次 LLM 串行，群明显慢。

**方案**

把「谁该被叫醒」抽成 `SummonQueue`，扇出按三波执行：

| 波次 | 谁 | 方式 | 理由 |
| --- | --- | --- | --- |
| 1 | 被用户点名 | 串行 | 必须开口；后者应看到前者发言 |
| 2 | 在场未点名 | **并行** | 只是顺带看一眼，拿同波次互不可见换速度 |
| 3 | 被同事发言再次 `@` | 串行 | 二次叫醒，同样要顺序语义 |

**关键实现细节**

- **同步占名额**：并行波次派发前必须先用 `reserve()` 登记每个成员。
  否则同波次的人互相 `@` 时，会因为「对方还没开始跑」而漏掉二次叫醒。
- **排除发言者**：`@everyone` 是叫别人看，不含自己，`summonFrom(mentions, speakerId)` 要过滤。
- **判断重复入队只看 `enqueued`**：不能因为「这人已经跑过」就跳过——
  跑过的人被再次点名，正是我们要支持的场景。
- **防环**：`ROOM_MAX_RUNS_PER_MEMBER = 2`，一轮内同一人最多被叫醒两次。

**取舍**：波次 2 的人互相看不见对方这一轮的发言。补偿手段是简报里带上
「这一轮已经有人说过」段落（来自波次 1 与更早），所以信息不会完全断掉。

### 决策十:工作台写操作走「服务层 + 工具」两层

**问题**：规格要求智能体能在对话里替用户建同事、建群、拉人。
直觉做法是让工具直接调 `AgentRegistry.create()`，但那样权限规则会散落在每个工具里。

**方案**：抽 `Workbench` 服务层，工具只做「参数整形 + 调服务 + 措辞」。
所有权限规则集中在服务层：

| 规则 | 位置 |
| --- | --- |
| 拒绝重名（要求改用 update_*） | `createAgent` / `createRoom` |
| 合并写入、空字符串不覆盖 | `AgentRegistry.update()` |
| 改群要求调用者已在群里 | `updateRoom` / `postToRoom` |
| 不能把成员删空 | `updateRoom` |
| 不存在的 id 明确报错 | `resolveMemberIds` |
| **没有删除同事 / 解散群的入口** | 服务层压根不提供这两个方法 |

**为什么「没有方法」比「检查权限」更可靠**：工具是从服务层的方法生成的，
服务层没有 `deleteAgent`，模型就不可能通过任何参数组合删掉同事。
权限不是靠 if 判断守住的，是靠**能力压根不存在**。

**配额放在回合状态里**：`TurnState.workbench` 记录本轮已建数量，
每回合重置。这样「一轮最多建 2 个」不依赖数据库计数。

**智能体也需要先「看得见」才能改**：实测发现模型会拿 `recall` 和 `list_files`
乱找群 id。补了 `list_workspace` 工具，一次列出同事 / 群 / 分组与 id。

## 5. 上下文预算分配

`allocateSections()` 解决「有限的 token 怎么分给各段」。

### 5.1 预算常量

```ts
DEFAULT_BUDGET = {
  total: 60_000,          // 总预算
  recentLimit: 30,        // 最多取多少条近期消息做候选
  compactionTrigger: 12,  // 攒够多少条待压缩消息就触发
  reserveRecent: 30,      // 压缩时保留多少条最新消息不动
  sections: {
    memory:    { min:  2_000, max:  5_000 },
    retrieval: { min:  5_000, max: 20_000 },
    compacted: { min:  5_000, max: 20_000 },
    recent:    { min: 20_000, max: 50_000 },
  },
}
```

### 5.2 分配算法

```
1. 扣除固定开销：instructions + task + files
2. 剩余额度 available
3. 先给每段保底 min（按比例缩放，保证总和不超过 available）
4. 按优先级把余量分给各段，直到达到 want 或 max：
       recent > memory > retrieval > compacted
5. 最终每段取 min(分配额, 实际需求)
```

**优先级理由**:近期原文是保真度最高的信息，宁可牺牲早期日志的召回也要保住它。

### 5.3 分配到段内的行为

| 段 | 超预算时 |
| --- | --- |
| 画像 / 关于你 / 日志 / 检索 | `truncateToTokens()` 截断加省略号 |
| 最近原文 | 按**原子组**从后往前保留，整组丢弃 |
| 每段的实际用量 | 记进 `ContextStats.sections[]`，通过 SSE 推给前端展示 |

### 6.4 安全约束

所有文件工具共用 `resolveInside()` 沙箱校验：

```ts
const absolute = resolve(root, path);
const rel = relative(root, absolute);
if (rel.startsWith('..') || isAbsolute(rel)) throw new Error('path escapes the sandbox root');
```

实测验证过路径穿越被拒绝（`../etc/hosts` → 报错）。

## 7. 并发与生命周期

### 7.1 回合锁

`AgentRuntime` 为每个 agent 维护一把锁（`Set<string>`），同一时刻只允许一个回合：

- 冲突时抛 `AgentBusyError` → HTTP 层返回 409
- 锁在 `finally` 中释放
- 释放后会检查收件箱，有积压就自动触发 `drainInbox()`

### 7.2 取消

- SSE 响应 `close` 事件 → `AbortController.abort()`
- 信号透传到 `LLMProvider.chat()` 的 `fetch` 与工具执行
- 前端「停止」按钮同样走 abort

### 7.3 启动顺序

```
Electron 主进程
  └─ import(dist/server/http.js)          ← 必须已构建
      └─ createAgentServer({ port: 0 })   ← 随机端口，避免冲突
          ├─ ensureDefaultAgent()         ← 播种预置智能体
          ├─ ensureSeedRooms()            ← 播种预置房间
          └─ listen(0, '127.0.0.1')
  └─ BrowserWindow.loadURL(handle.url)
  └─ window-all-closed → handle.close()
```

**为什么端口用 0**:避免与用户正在运行的其他服务冲突；Electron 拿到真实端口后再导航。

## 9. 已知限制

| 限制 | 影响 | 可能的解法 |
| --- | --- | --- |
| 检索是词法而非语义 | 换种说法问旧记忆可能搜不到 | 引入 embedding 或混合检索 |
| token 估算非精确 | 极端情况下可能低估 | 用 provider 返回的 `usage` 做闭环校准 |
| 压缩是有损的 | 特别早的细节会消失 | 靠 `remember` 显式固定重要事实 |
| 单进程内存缓存 | 多实例部署会不一致 | 当前定位是本地应用，可接受 |
| 群成员上限 6 | 大群不可用 | 按产品规格设定，可调 |
| 无鉴权 | 仅监听 127.0.0.1 | 如需局域网访问要加 token |
